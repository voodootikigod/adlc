# Spec — Context-Rot Handoff Threshold Calibration & Active-Epoch Telemetry

Scope: Fix false-positive context-rot handoff firing in Claude Code and Codex adapters. This spec is split into **Phase 0** (§1.2–§1.3, AC0) — an immediate, independently-shippable hotfix that retires the uncalibrated byte-threshold OR-join and the `+Infinity` scan-budget trap, and closes the recovery-CLI-is-itself-denied gap that turned the last false-positive into a total, un-self-recoverable lockout of Claude Code and Codex — and **Phase 1** (§2–§4 AC1–AC9) — the target design for lossless binary chunk framing, unrounded exact occupancy threshold comparisons, pinned tokenizer-driven exact occupancy verification, canonical pending payload serialization, strict semantic calendar date and sentinel validation, deterministic canonical JSON signatures, adapter-owned host-verified compaction provenance (MAC-bound, non-tool-writable), lock-protected unified scan-and-ledger transactions with crash recovery, bounded streaming reverse seek without token-based early termination, normative per-adapter context projections, and fail-closed error handling with positive-registry read-only recovery — which depends on host envelope capabilities Claude Code and Codex do not yet expose (§1.1, §2's banner). Phase 0 does not depend on Phase 1 and is scoped, implemented, and reviewed as an independent unit.

---

## 1. Problem & Root Cause

The context-rot handoff gate (`@adlc/context-handoff`) denies all state-mutating operations once a session enters the `handoff` (60%) or `hard` (80%) band.

In Claude Code and Codex, the gate currently fires prematurely after ~2 tool calls in fresh sessions because:
1. **Missing Host Telemetry:** Hook payloads on Claude Code and Codex expose no live context occupancy percentage or token counts.
2. **Monotonic Transcript Growth:** `transcript_path` is an append-only JSONL log on disk that never truncates across compactions.
3. **The 256 KiB Truncation Trap:** `MAX_SCAN_BYTES` was equated to `HARD_BYTES` (256 KiB), and exceeding it set `observed.depth = +Infinity`, hard-locking any session with > 256 KiB on disk regardless of tool count.
4. **Uncalibrated Absolute Byte Thresholds in OR-Join:** `evaluateBands` OR-joins `pct`, `depth`, and `bytes`. Fixed thresholds (`WARN_BYTES=128KiB`, `HANDOFF_BYTES=192KiB`, `HARD_BYTES=256KiB`) are exceeded at turn 0-2 by system prompts, MCP schemas, and rules.

### 1.1. Scope Split: What Ships Now vs. What Requires Host Support

Root-cause items 3 and 4 above are reproducible today, entirely within this repo's own code (`packages/context-handoff/lib/bands.mjs`, `thresholds.mjs`), and are fixable without any change to Claude Code's or Codex's actual hook payload. Section 2 of this spec (the host-authenticated compaction provenance, MAC-bound ledger, lock protocol, and pinned-tokenizer exact-occupancy design) additionally requires host envelope fields — `K_host`, `input.host_lock_fd`, `host_live_tokens`/`host_capacity_tokens`, `occupancy_bind_mac`, a privileged `input.source === 'host'` IPC channel — **that do not exist in Claude Code's or Codex's PreToolUse hook payload as of this writing.** Deploying §2 as a hard requirement (as AC1–AC9 currently do, `Mandatory ... non-optional`) on an unmodified host causes every session to enter Hard-Degraded Mode on its very first evaluation — recreating the exact production outage this spec exists to fix.

This spec is therefore split into two independently-tracked phases. Neither is deleted or descoped by the other:

- **Phase 0 — Immediate Hotfix (§1.2, this section):** ships now, requires no host change, targets root-cause items 3 and 4 directly. This is the change that unblocks the currently-stranded sessions and is the minimum bar for closing this ticket.
- **Phase 1 — Host-Protocol Design (§2 in full):** the HMAC/ledger/lock/exact-tokenizer architecture remains the target design for precise occupancy tracking, but is gated on real host support landing in Claude Code and/or Codex. §2.7 already states the required deployment order (host support before adapter enforcement); AC1–AC9 MUST NOT be treated as satisfied, and enforcement MUST NOT be enabled, until a concrete host implementation of those envelope fields exists and is verified against this adapter. Until then, Phase 1 is a design document, not a shippable requirement.

Every rule below that can send a session to Hard-Degraded Mode — in both phases — is additionally bound by the Recovery Exception in §1.3: Hard-Degraded Mode may deny ordinary mutations, but it MUST NEVER be able to deny the operator's own recovery path or reproduce a total-lockout outage.

### 1.2. Immediate Hotfix (Phase 0 — deployable now, no host capability required)

Targets: `packages/context-handoff/lib/bands.mjs`, `packages/context-handoff/lib/thresholds.mjs`, and any adapter call site that feeds `observed.bytes` or an unbounded/`+Infinity` `observed.depth` into `evaluateBands`.

1. **Retire byte thresholds from the OR-join for Claude Code and Codex.** `WARN_BYTES` / `HANDOFF_BYTES` / `HARD_BYTES` were calibrated against nothing (root cause 4) and are tripped by system-prompt/MCP-schema/rules overhead before any real tool-call pressure exists. Claude Code and Codex adapters MUST stop populating `observed.bytes`; `evaluateBands` treats an absent signal as `{ warn: false, handoff: false, hard: false }` for that signal already (see `bands.mjs`'s `absent` handling), so omitting it is sufficient — no change to `evaluateBands` itself is required. (`bytes` support may remain for other, already-calibrated adapters; this hotfix scopes the removal to the two affected adapters' call sites.)
2. **Retire `MAX_SCAN_BYTES` as a separate low ceiling — it was the actual bug, not just its `+Infinity` consequence.** The root cause (§1 item 3) was `MAX_SCAN_BYTES` being equated to `HARD_BYTES` (256 KiB): a fresh session's baseline system-prompt/MCP-schema/rules text routinely exceeds 256 KiB on turn 0-2 in a normal Claude Code or Codex session with several plugins/skills loaded — this is not a rare or adversarial case, it is the common case this incident was filed about. Fixing only the *consequence* (no more `+Infinity`) while leaving `MAX_SCAN_BYTES` at 256 KiB would still deny every ordinary mutation on every evaluation of such a session, indefinitely — the same baseline record exceeds the same cap every time, so the scan can never complete and the lower-bound-restricts-to-recovery-only rule (below) would never lift. That is not a fix, it is the same lockout with better diagnostics. **`MAX_SCAN_BYTES` is retired as a distinct constant.** The scan's only budgets are `MAX_ACTIVE_CONTEXT_BYTES` (8 MiB, §2.2.3 — already generous, shared with Phase 1) and `MAX_SCAN_WALL_MS` (§2.2.3's wall-clock budget) — a byte ceiling two orders of magnitude larger than the failure case, and a time ceiling that a baseline in the hundreds-of-KB-to-low-single-digit-MB range comfortably fits within on ordinary hardware (sequential reads of a few MB complete in low tens of milliseconds even on modest storage). The current failure mode sets `observed.depth = +Infinity` when the transcript scan exceeds this budget, which `evaluateBands`'s out-of-domain/malformed handling then treats as past every band — an unbounded, unproven value masquerading as certainty. Because the scan reads newest-to-oldest, the count accumulated before a deadline is a **lower bound**, not an exact answer, in either direction: it can correctly prove `HARD_DEPTH` (more calls only make a hard band more true), but it cannot prove the session is *safe* — an unscanned older remainder can contain arbitrarily more calls. When the scan budget is exceeded before reaching either a compaction boundary or start-of-file, the adapter MUST report the count actually accumulated before the budget was hit (never `+Infinity`), and:
   - **Phase 0 boundary policy (this was previously undefined and must be stated normatively, not left implicit):** Phase 0 has no `K_host`, no host events, and no way to MAC-verify a compaction boundary — §2.1.2's authentication scheme is entirely Phase 1 machinery. Every well-formed record that merely *looks* like a compaction boundary is therefore, unconditionally, "unregistered" under §2.1's own general rule ("a record carrying compaction-like keys that lacks a MAC-verified host event is strictly treated as ordinary dialogue/payload text; the scanner does NOT reset the epoch on it") — that rule already covers Phase 0 exactly as written; it does not need new text, only explicit acknowledgment that it is the answer. **Consequently, Phase 0's backward scan never stops early at a compaction boundary — it always scans toward start-of-file (or the resource budgets below), treating the entire on-disk transcript as one continuous epoch.** This is the conservative, safe direction consistent with this document's governing principle (never claim more certainty than is proven): overcounting depth for a heavily-compacted long session denies sooner than strictly necessary, which is a safe failure mode, not the false-negative "the scanner trusted a forged marker and undercounted" failure mode a naive implementation risks by contrast.
   - **Honest scope of this guarantee, corrected to account for the boundary policy above:** Phase 0 is a *stateless, single-shot* scan by design (§1.2's own contract: "no ledger, no lock... using only the fields Claude Code and Codex already provide today") — it has no cross-evaluation checkpoint to resume from, so raising the ceiling to 8 MiB makes the *reported* incident (a routine, common-case baseline in the hundreds-of-KB range) fully and completely fixed. But because Phase 0 never recognizes a compaction boundary, its 8 MiB ceiling is a **cumulative on-disk transcript size limit, not merely a single-baseline-record limit** — a long-running session that the host has compacted several times, but whose underlying transcript file retains full pre-compaction history, can reach 8 MiB of cumulative content even with a small *currently active* epoch, and would face the same scan-incompleteness restriction as a genuinely oversized fresh baseline. This is a real, broader residual than "pathological baselines" alone, and it is disclosed as such rather than understated: such a session is never stranded (`pwd` and the Recovery Exception remain reachable, same as every other restricted case in this spec, and it fails safely rather than falsely-allowing via a trusted-but-unauthenticated boundary), but its ordinary mutators do remain restricted until Phase 1's authenticated compaction provenance (§2.1) and cross-evaluation, resumable, ledger-backed scan (§2.1.4's chunk-chain commitment, once implemented) land. Given `MAX_ACTIVE_CONTEXT_BYTES` is roughly 30× the size that triggered the actual production outage, and a session accumulating 8 MiB of cumulative transcript across several compactions is a materially rarer, longer-lived case than the reported fresh-session regression, this is judged an acceptable, clearly-bounded scope line for the immediate hotfix rather than a reason to delay it pending a full persistent-scan redesign — but it is a real limit on what "fixes the reported outage" means, not a hypothetical one.
   - **the threshold for trusting an incomplete count is `HANDOFF_DEPTH`, not `WARN_DEPTH`.** `WARN` still permits mutations (§2.4.1's `handoffDenyActive` only denies at `handoff`/`hard`), so a lower bound sitting in `WARN` territory (e.g. 20–29) is *not* safe to "use normally" — the unseen older remainder could push the true depth past `HANDOFF_DEPTH` or `HARD_DEPTH`, and allowing on an unproven WARN reading would silently fail open exactly where protection matters most. Only a lower bound that already reaches `HANDOFF_DEPTH` is safe to act on as-is (more unseen calls only make a deny/handoff more correct, never less).
   - if the lower bound has **not** reached `HANDOFF_DEPTH`, the adapter MUST NOT claim a full allow from an incomplete scan — mutation tools other than the Recovery Exception and the Inspection Bash Exception (§1.3, both evaluated first, before this restriction) remain denied (other inspection tools stay allowed) until a scan completes and establishes a true, non-partial depth. This applies even when the lower bound is in `WARN` territory. This is deliberately narrower than Hard-Degraded Mode: it does not zero out `observed.depth` or set `NaN`, and a subsequent evaluation that manages a complete scan resolves normally.
3. **Fresh/low-usage sessions must never trip any band on turn 0–2.** This is the regression the hotfix exists to close; see AC0.

This hotfix requires no ledger, no lock, no HMAC key, and no new host envelope field — it is a bug fix to already-shipped threshold logic, using only the `transcript_path`, `session_id`, and `tool_name`/`tool_input` fields Claude Code and Codex already provide today.

### 1.3. Recovery Exception (normative for every Hard-Degraded/deny path, both phases)

The production incident this spec responds to denied **every** Bash invocation on a hard-degraded session — including `pwd` and the operator's own `node packages/context-handoff/bin/handoff.mjs bypass|unlock|repair` recovery commands. §2.6's existing "positive-registry read-only recovery" only allowlists file-inspection tools (`View`, `read_file`, etc.); it does not allowlist the one thing an operator actually needs to run to get unstuck. That gap is not acceptable in either phase:

- **Tool-identity gate, checked before command-string matching, not after — and grounded in the real, already-deployed wire shape, not a re-derived assumption (an earlier draft of this section assumed a single literal `execute_command` identity and a single `tool_input.command` field for Codex; the real integration is materially different, per `plugins/adlc-codex/hooks/adlc-handoff-gate.mjs`, which already ships and is tested):**
  - **Claude Code:** the command-string grammar below applies only when `input.tool_name` (the single field this host uses) is exactly `Bash` or `Shell` — matching this repo's own existing check in `plugins/adlc-claude-code/hooks/adlc-hook.mjs` (`toolName === 'Bash' || toolName === 'Shell'`), reused rather than re-derived.
  - **Codex:** the real payload's tool-name value may appear under any of several field names (`tool_name`, `toolName`, `tool`, `name`, `recipient_name`) — this exception reuses `toolNameOf` from `plugins/adlc-codex/hooks/adlc-handoff-gate.mjs` to read it, since that part is purely about *finding* the name, not judging it. **Judging it is different, and this exception deliberately does NOT reuse that file's `isShellToolName` classifier, even though it's the real, already-shipped Codex shell-tool test** — `isShellToolName`'s broad, suffix-anchored `/(^|\.)(bash|shell|exec|exec_command|run_command|write_stdin)$/i` is calibrated for the *denial* side of this system, where over-inclusion is the safe direction (catch anything that might be a shell so it gets properly scrutinized). Reusing the identical predicate for an *unconditional-allow* exception inverts that safety property — over-inclusion here is dangerous, not safe — and it has two concrete problems for that purpose: (1) `write_stdin`/`functions.write_stdin` deliver `chars` to an **existing** process (a REPL, editor, or whatever the session left running), which is not "execute a fresh, standalone `pwd`/recovery command" at all — the same literal text means something entirely different depending on that process's state, which this exception has no way to inspect or constrain; (2) the `(^|\.)` anchor permits *any* prefix before the dot, so a tool registered as `evil.exec_command` (or any other attacker-chosen namespace ending in `.exec_command`) passes the identity check — the earlier claim that this anchor "stops spoofing" was wrong; it only requires a dot boundary, not a trusted prefix.
  - **This exception's own Codex identity check is therefore a separate, narrower, purpose-built exact allowlist — not a regex, not a reused classifier:** `exec_command`, `functions.exec_command` (the literal string only — no other prefix before `.exec_command` matches), `exec`, `Bash`, `bash`, `Shell`, `shell`. `write_stdin`/`functions.write_stdin` and `run_command` are explicitly excluded — the first for the reason above, the second conservatively (its exact standalone-execution semantics relative to `exec_command` are not independently verified here, so it is left out rather than assumed safe). A `multi_tool_use.parallel` envelope or any other composite/nested tool call — even one that carries an eligible shell name as a *child* call inside it — is a non-match at the top level; this exception matches only a single, standalone, top-level invocation of one of the exact names above, never a name found nested inside another tool's payload (unlike `hasShellToolAnywhere`'s recursive search, which exists for the opposite, safe-to-over-include, denial-side purpose).
  - Command-text extraction is host-specific, not one fixed field on both — see the detailed contract two bullets below (Claude Code: single `tool_input.command`; Codex: `collectCommandText` requiring exactly one non-empty candidate).
  - This is not the same as Phase 1's `input.source === 'host'` positive-provenance check (§2.5), which requires a privileged host envelope field Phase 0 does not have — it is the check actually available today, and it is deliberately weaker than Phase 1's cryptographic provenance check: it defends against a *tool naming itself* outside the recognized identity patterns above, not against a compromised or malicious implementation *of* the genuine host-dispatched shell tool itself (which Phase 0 has no mechanism to detect, the same limitation every other shell-classified path in this document already has).
- Before any other Hard-Degraded/deny check (band evaluation, lock timeout, ledger/MAC failure, host-protocol field absence in Phase 1, or Phase 0's own threshold logic), the adapter MUST recognize an invocation of the mutating tool passing the tool-identity gate above whose command line matches this normative grammar, and MUST allow it, regardless of band state. **The match is against a single shell command string, not a structured argv array — an earlier draft of this rule specified an argv-only, no-shell-string grammar that no real Bash/`execute_command` payload can ever satisfy (including this section's own diagnostic-message example), which would have silently converted the "unconditional" exception into one that can never actually match. Corrected below.** **Where that string comes from is host-specific and is the line-50 contract, not a fixed field path (an earlier draft of *this* sentence separately, and wrongly, said the fixed field was `tool_input.command` on both hosts — retired along with the argv-only mistake): Claude Code delivers it as a single, unambiguous `tool_input.command` string. Codex does not — its command text may appear under any of `command`/`cmd`/`input`/`script`/`chars`, potentially nested, so this exception obtains candidates via `collectCommandText` (the real, already-shipped collector in `plugins/adlc-codex/hooks/adlc-handoff-gate.mjs`, reused for extraction only — not `isShellToolName`, which remains excluded per the identity-gate rule above) and requires exactly one non-empty candidate string for a standalone top-level invocation to be eligible; zero candidates, or more than one (a composite/multi-field envelope), is a non-match, consistent with the nested/composite exclusion already stated for tool identity.**
  - **Platform scope, disclosed explicitly (the same kind of honest, bounded scope line as §1.2.2's 8 MiB scan ceiling, not a silently-ignored gap):** the grammar below targets POSIX-compatible shells — macOS, Linux, and WSL on Windows — where `process.execPath`/script paths are `/`-rooted and single-quoting has the literal semantics `PATH_GRAMMAR` relies on. **It does not support native Windows (`cmd.exe`/PowerShell)**, whose drive-qualified/UNC paths, different absolute-path predicate, and entirely different quoting/escaping model (PowerShell's single-quote *does* behave literally, similar to POSIX, but `cmd.exe`'s does not — this is a different shell family with a different injection surface, not just a different path spelling, and needs its own from-scratch grammar rather than a patch to this one) are out of scope for this hotfix. On native Windows, this exception does not reliably match any diagnostic command Phase 0 can print, so an operator there is not fully covered by this specific escape hatch until a dedicated Windows grammar is designed as tracked follow-up work — the same explicit, disclosed, non-silent scope boundary this document already uses elsewhere, not a claim that Phase 0 fixes the reported outage on every possible platform.
  - **Two named grammars, defined once here and referenced by name everywhere else in this document — never restated with different characters, which is precisely how earlier drafts of this section drifted out of sync with themselves across several review rounds:**
    - **`VALUE_GRAMMAR = [A-Za-z0-9_./=:-]+`** (unquoted only). Applies to the subcommand token and every flag/value token (third token onward). The `:` is included specifically because `unlock --started-at` MUST reproduce the lock's ISO 8601 timestamp (e.g. `2026-08-15T12:34:56.789Z`) byte-for-byte to pass the CLI's own exact lock-field comparison (§ `handoff.mjs unlock` usage); a colon has no special interpretation to any POSIX-family shell outside of parameter-expansion syntax (`${...}`), which this grammar already excludes by omitting `$`/`{`/`}`. Every legitimate value in this position — session ids per `isSafeSessionId`'s `/^[A-Za-z0-9._-]{1,128}$/`, ticket ids, content hashes, ISO timestamps — is representable in `VALUE_GRAMMAR`; a flag value requiring anything outside it, such as `--unbound-reason` free text, is simply **not eligible for this exception** and falls through to ordinary mutation-gate evaluation like any other Bash call.
    - **`PATH_GRAMMAR = [A-Za-z0-9_./=-]+` OR a single-quoted form `'...'` whose content is any byte except a literal single-quote, NUL, or newline** (POSIX single-quote semantics: fully literal, no escapes or substitutions recognized inside — quoting here introduces no new interpretation, only a wider literal-byte range). Applies **only** to the first two tokens (interpreter, script), because real absolute paths legally contain characters outside the base alphabet (spaces, Unicode) and both tokens are always adapter-controlled — never attacker-chosen, always exactly what the adapter's own `process.execPath`/package-path resolution produces — so widening *only these two positions* does not reopen the injection surface `VALUE_GRAMMAR` exists to close. A quoted token containing a literal single-quote is not representable and is rejected (the adapter's install path MUST NOT itself contain an apostrophe for this exception to remain usable — a disclosed limitation, not a silent gap).
    - **This bullet governs *unquoted* text and `VALUE_GRAMMAR` tokens only — it does not restrict the literal byte content inside a properly single-quoted `PATH_GRAMMAR` token, which is governed entirely by the `PATH_GRAMMAR` bullet above (any byte except a literal single-quote, NUL, or newline) and nothing else.** Outside of that quoted span: single quotes are never accepted except as `PATH_GRAMMAR`'s own delimiters; double quotes are never accepted in any position, quoted or not (there is no double-quote-delimited form anywhere in this grammar); and for `VALUE_GRAMMAR` tokens, any character outside `[A-Za-z0-9_./=:-]` — parentheses, backticks, `$`, `;`, `|`, `&`, `<`, `>`, backslash, newline, any quote character, or anything else not explicitly listed — is an automatic non-match. (Concretely: a `PATH_GRAMMAR` token like `'/Users/alice/needs-$-or-&-in-path/adlc'` is valid — those characters are literal quoted bytes, not shell syntax the matcher is interpreting — while the identical characters unquoted, or appearing in a `VALUE_GRAMMAR` position, are rejected.) The matcher never attempts to enumerate what's *dangerous* in the positions this rule governs, only what's *sufficient*, so no future shell feature can slip through an incomplete denylist. **Before any tokenization is attempted, the raw string is checked for a CR (`0x0D`) or LF (`0x0A`) byte anywhere in it — including between what would otherwise look like two valid tokens, not only inside one — and the presence of either is an immediate, unconditional non-match for the whole string.** This check happens first because a newline is a command separator to the shell that eventually executes an allowed string (equivalent to `;`): treating it merely as "one more separator" during tokenization — e.g. splitting on a generic `\s+`/whitespace-class regex, which by default includes `\n` — would let `.../handoff.mjs bypass --session\n/tmp/evil --write` tokenize into an apparently-valid sequence while the shell instead executes two separate command lines, the second entirely attacker-controlled. **The only recognized token separator, once the newline check has passed, is a single ASCII space (`0x20`)** — not a tab, not any other whitespace character, not a run of multiple spaces treated as one. The adapter never hands the string to a shell for this match — it only tokenizes (space-separated, outside of a `PATH_GRAMMAR` quoted span, which is the only recognized exception to plain space splitting) and compares.
  - **The first token** must match `PATH_GRAMMAR` and, once unquoted, must be an absolute path (starts with `/`) — `fs.realpathSync` resolves a filesystem path, it does not perform `PATH` lookup, so a bare `node` token (no leading `/`) is rejected by the grammar itself before any resolution is attempted, rather than being handed to `realpathSync` and throwing `ENOENT` (which would deny the exception's own canonical command in any worktree without a literal `./node` file — a mistake an earlier draft of this section made). The resolved (`fs.realpathSync`) value MUST equal the adapter's own realpath-resolved `process.execPath`. **Every Hard-Degraded/deny diagnostic message (§1.3's later bullet) emits this same resolved absolute path, single-quoted per `PATH_GRAMMAR` whenever it contains a character outside the unquoted alphabet** — there is no PATH-resolution ambiguity to specify because the diagnostic already contains the exact right string to copy.
  - **The second token** must match `PATH_GRAMMAR`, likewise be an absolute path once unquoted, resolved via `fs.realpathSync` re-checked fresh at match time (not cached from an earlier evaluation, to close the symlink-swap/TOCTOU window on the *path identity* check), and MUST equal the package's own `packages/context-handoff/bin/handoff.mjs` (also realpath-resolved, so the comparison is between two canonical absolute paths regardless of either process's working directory). **Every diagnostic message likewise emits this script token as its own resolved absolute path, single-quoted per `PATH_GRAMMAR` when needed, never a repo-relative form** — an earlier draft of this section printed a relative path here, which a matcher resolving from a different working directory (e.g. a nested hook `cwd`) could fail to match, again reproducing the lockout this section exists to prevent. Matching and eventual execution MUST resolve both tokens from the same, adapter-controlled working directory (or use these absolute forms directly, which need no `cwd` at all) — never a tool-supplied or otherwise variable one.
  - **The third token** must match `VALUE_GRAMMAR` and be exactly one of `bypass`, `unlock`, `repair`, `write`, `resume` (no others). **Tokens from the fourth onward alternate strictly between a flag-name token and, for every non-boolean flag, exactly one following flag-value token** — flag *names* and flag *values* are distinct token classes, not the same check applied twice (an earlier draft of this section conflated them, which would have rejected every value, including the session id, as though it had to itself be a flag name):
    - A **flag-name token** starts with exactly `--` and must be one of the subcommand's own whitelisted flag names below. Recognizing `--flag=value` as a single token is **not** supported by this exception (only `--flag value` as two space-separated tokens); an invocation using `=` form falls through to ordinary evaluation — this costs nothing in practice because the diagnostic message the adapter itself prints always uses two-token form.
    - Boolean flags (`--write`, `--json`) take no following value token. Every other whitelisted flag takes exactly one following **flag-value token**, which must match `VALUE_GRAMMAR` (it is not required to itself be a flag name) — **with one additional, semantic binding rule, not merely a grammar rule: a `--session` flag-value (present in every one of the five subcommands) MUST equal `resolveSessionId(input)` — this session's own resolved identity — exactly, character for character; a `--session` value that is grammatically valid but names a *different* session is a non-match, same as any other rejected token.** Without this, matching only on shape would let this session's own degraded state authorize a recovery command that targets an unrelated session's lock/deny/final state — the exception exists to let a session recover itself, not to grant a blanket cross-session capability. If `resolveSessionId(input)` itself returns nothing (the no-safe-session-id branch above), there is no value a `--session` token could equal, so no `--session`-bearing command matches at all — consistent with that branch's diagnostic never printing one. **`--deny-session` (meaningful only for `resume`) is explicitly exempt from this same-session binding:** `resume`'s entire documented purpose is a *different* session (the consumer, bound via `--session` to this session's own identity as above) consuming a deny left by an *other*, prior session (the denier, named by `--deny-session`) — restricting `--deny-session` to equal the current session would make `resume` permanently unusable through this exception. `--deny-session` still must satisfy `VALUE_GRAMMAR`; it grants no broader capability than the CLI's own `resume` semantics already do (consuming a deny requires that other session's own final/marker state to already validly exist — an attacker cannot manufacture a useful resume against an arbitrary unrelated id).
    - Per-subcommand whitelisted flag names, taken directly from the real CLI (`packages/context-handoff/bin/handoff.mjs`) — this exception allowlists exactly this set, no more:
      - `bypass`: `--session`, `--ticket`, `--write`, `--json` (**not** `--unbound-reason`: that flag's value is free text outside `VALUE_GRAMMAR` by design, per §1.3's introduction — an unbound bypass is not reachable through this exception and falls through to ordinary evaluation, same as any flag/value combination this grammar doesn't cover)
      - `unlock`: `--session`, `--pid`, `--started-at`, `--host`, `--nonce`, `--write`, `--json`
      - `repair`: `--session`, `--ticket`, `--content-hash`, `--host`, `--write`, `--json`
      - `write`: `--session`, `--ticket`, `--host`, `--content-hash`, `--write`, `--json`
      - `resume`: `--session`, `--deny-session`, `--write`, `--json`
    - A duplicate flag name, a flag name unknown to the given subcommand, a value-taking flag with no following token (or followed immediately by another flag name), or a boolean flag followed by a stray value token, is a non-match for the same reason an unrecognized flag is: this is a fixed, closed grammar, not a general CLI-argument parser.
  - **Honest scope of this defense — do not overclaim it:** this closes decoy/wrong-path/injection attacks (a string that merely *resembles* the recovery command, or tries to smuggle extra commands alongside it) and the interpreter/path *identity* TOCTOU window at match time. **It does not, and — within Phase 0's own stated constraints (§1.2: "no ledger, no lock, no HMAC key, no new host envelope field") — cannot, verify the *content* of the script that identity check resolves to.** Phase 0 has no host-owned, non-tool-writable storage to anchor a trusted content digest in; anything Phase 0 could write to hold such a digest (e.g. a file next to `handoff.mjs`) lives in the same tool-writable workspace as the script itself, so a prior Write that plants a modified `handoff.mjs` could just as easily update an adjacent digest file to match — that is not a real defense, and an earlier draft of this section incorrectly claimed it as one. **This residual — a workspace-writable `handoff.mjs` could in principle be tampered with by a prior Write before the exception is ever invoked — is real, is not closed by Phase 0, and is the same class of gap as Phase 1's entire host-capability dependency (§1.1): a genuine content-attestation defense needs a host-owned, non-tool-writable integrity anchor, which is Phase 1-shaped and out of Phase 0's reach.** It is *not*, however, a novel hole this exception introduces: an attacker who can already Write arbitrary files into the workspace can already plant malicious code anywhere else in this repo too (a CI script, another hook, a dependency) — the Recovery Exception's identity check narrows what such an attacker could exploit *through this specific path* to exactly the same trust boundary the rest of the repo already operates under, it does not widen it. Closing this fully is tracked as Phase 1 follow-up work (a host-attested launcher), not a Phase 0 blocker, on the same "detect torn/uncertain state, never silently claim more than is proven" principle used throughout this document.
- **Everywhere else in this document, "`Bash`/`execute_command`" is informal shorthand for "the tool-identity gate above" — Claude Code: `Bash`/`Shell` via `input.tool_name`; Codex: `toolNameOf(input)`'s result (read across `tool_name`/`toolName`/`tool`/`name`/`recipient_name`) tested for membership in this exception's own exact recovery-only set (`exec_command`, the literal `functions.exec_command`, `exec`, `Bash`, `bash`, `Shell`, `shell`) — **never** `isShellToolName`, which is the denial-side's intentionally broader classifier and MUST NOT be called anywhere in the Recovery Exception or Inspection Bash Exception's own matching path, for the safety-direction reason given above.** This applies to every subsequent mention in §1.3/§4 AC0/AC9; §2.5/AC7's pre-existing Phase 1 Mutating-Set table still names `execute_command` literally and needs the same correction before Phase 1 implementation — tracked as an addition to §2.3's "open cut-points" note, since it's Phase 1 scope, not a Phase 0 blocker (Phase 0's own gate, above, is already correct).
- **Inspection Bash Exception (evaluated by the same rule, alongside the Recovery Exception, not a separate mechanism — including the same tool-identity gate above):** an invocation whose command line is the exact literal `pwd` (no arguments, no shell metacharacters, no chaining) is likewise allowed regardless of band state or scan/depth completeness. This exists because §1.2.2/§2.2.3's incomplete-scan lower-bound rule (below) can otherwise restrict *all* mutating tools — `pwd` included, since it is classified under the Mutating Set — even on a fresh session whose scan simply couldn't finish within budget due to a large baseline record; without this carve-out, that case would deny the exact command the original outage denied. `pwd` is chosen deliberately narrowly: it reads no file content, mutates nothing, and cannot itself consume meaningful additional context, so allowing it unconditionally does not reopen any of the protections this spec exists to preserve. It is not a general "safe commands" allowlist — extending it to `ls`/`git status`/etc. is out of scope for this fix.
- **This exception authenticates command *shape*, not operator *intent* — that is a known, bounded limitation, not an oversight.** The CLI's own `ADLC_MANIFEST_KEY` requirement for any mutating `--write` (§ handoff.mjs usage) is the same authorization boundary every other mutating manifest operation in this repo already relies on; the Recovery Exception does not weaken it, it only restores the operator's ability to *reach* that already-gated tool when a band would otherwise block the Bash call before the CLI's own check ever runs. It does not, by itself, prove a human rather than the degraded agent issued the command — if `ADLC_MANIFEST_KEY` is present in the agent's ambient shell environment (as it commonly is in a dev worktree), an agent can self-issue `bypass --write` as readily as an operator can. Two mitigations apply now, in Phase 0:
  1. Every allowed recovery-CLI invocation — dry-run or `--write` — the adapter MUST *attempt* to record to the manifest evidence trail (the existing `recordOrExit`/gate mechanism already used by `handoff.mjs`) tagged distinctly as `context-handoff-recovery-under-band`. This is a best-effort audit trail, not a guaranteed one, and this document says so explicitly rather than claiming "always auditable": **the `permissionDecision: "allow"` for a matching command is never gated on the audit record succeeding** — recording is attempted after the allow decision, and its own failure is logged as a diagnostic warning but MUST NOT convert the allow into a deny, and MUST NOT be described as leaving a durable record when it didn't. This is the one place in this spec where "record before returning" (§2.3's rule for a mutating `allow`) is deliberately not the rule: gating the Recovery Exception on successful audit-logging would let a failure in the *logging path itself* strand an operator exactly the way the original incident did, which defeats the entire purpose of this exception — availability of the escape hatch is a harder requirement than completeness of its audit trail. The residual gap (a recovery invocation during a manifest-write outage leaves no evidence) is accepted knowingly, not silently. AC0 asserts both directions: the audit record is present and correctly tagged on a normal successful recovery invocation, and a simulated recording failure (e.g. an unwritable manifest path) still allows the recovery command through while surfacing the diagnostic warning.
  2. This is not a novel weakening of protection: an agent with `ADLC_MANIFEST_KEY` in its environment could already self-authorize `handoff write`/`bypass` before ever reaching a degraded band. The Recovery Exception changes *when* that pre-existing capability is reachable (also under band pressure), not *whether* it exists.
  A stronger fix — a one-shot, host-authenticated recovery capability bound to session, subcommand, and expiry, requiring an explicit out-of-band operator approval step the agent process cannot generate itself — is Phase 1 target hardening, gated the same way as the rest of §2's host-protocol dependency (§1.1): it needs a host-provided approval channel that does not exist in Claude Code's or Codex's hook payload today.
  3. **Round-11/12/13 implementation note, disclosed at the same level of honesty as the two mitigations above:** `handoff bypass --write` persists a signed, session-bound grant (`packages/context-handoff/lib/bypass-grant.mjs`) the adapter reads back and consumes on the next mutation — without this, the diagnostic-printed recovery command executed successfully but changed nothing, reproducing the total-lockout outage this section exists to close. Because Claude Code and Codex resolve `@adlc/context-handoff` from the PROJECT's node_modules (§1.3's own identity-check residual, above), `ADLC_MANIFEST_KEY` never crosses into that package — each hook verifies the grant with its own trusted local twin (pre-secret-scrub, before any project-controlled import) and hands the adapter only a three-state verdict, never the key. Consumption is `unlinkSync` as the one-shot primitive (POSIX guarantees exactly one caller's removal succeeds), attempted only when no other reason already denies the call, so a grant is never spent on a mutation that was going to fail anyway. **Honest scope, not silently overclaimed:** this guarantees one winner per directory-entry incarnation, not cryptographic single-use — the signed payload carries no per-issuance nonce and Phase 0 keeps no consumed-grant ledger (per this section's own "no ledger, no lock" constraint), so a process that captured the exact signed bytes before consumption could in principle recreate the file and have it re-verify for the remainder of its TTL. This requires first defeating the SAME best-effort protected-path Bash defense already disclosed elsewhere in this document (an obfuscated write the literal-token classifier cannot see through) — not a novel hole this mechanism introduces on its own — and is closed the same way the identity-check residual above is: a host-owned, non-tool-writable integrity anchor, Phase 1 target hardening.
- **When `resolveSessionId` yields a safe session id** (the ordinary case), every Hard-Degraded/deny diagnostic message MUST include the literal, copy-pasteable recovery command for the current session, with **both** the interpreter and the script given as the adapter's own realpath-resolved absolute paths (e.g. `/usr/local/bin/node /Users/you/repo/packages/context-handoff/bin/handoff.mjs bypass --session <id> --write` — the actual absolute paths depend on the running environment and worktree location; neither a bare `node` nor a repo-relative script path is ever printed, since neither is guaranteed to match the matcher's identity check below). **Either path token MUST be emitted single-quoted whenever it contains any character outside `[A-Za-z0-9_./=-]`** (e.g. a worktree at `/Users/alice/My Project/adlc` prints `'/Users/alice/My Project/adlc/.../handoff.mjs'`, matching the matcher's bounded quoting allowance above); a path containing a literal single-quote character cannot be represented and is a disclosed limitation, not silently swallowed. Not just a description of why telemetry degraded.
- **Why the `--session <id>` value never needs quoting:** every value this exception ever needs to place in a `--session`/`--deny-session` position is already filtered through `resolveSessionId`/`isSafeSessionId`'s `/^[A-Za-z0-9._-]{1,128}$/` (§2.1.2) *before* it is ever considered a candidate session id — that pattern's character set is a strict subset of `VALUE_GRAMMAR`'s, so a successfully-resolved session id is unquoted-representable by construction; there is no case where a *valid* session id fails to match this grammar.
- **The no-safe-session-id branch, defined normatively (not left as an unenforceable blanket claim):** when `resolveSessionId` finds no candidate at all — `input.session_id`/`sessionId` absent or unsafe, and the transcript path's basename also not yielding a safe id — there is no identity to build a `--session <id>` recovery command around, for any grammar: the underlying `handoff.mjs` CLI itself requires a safe session id for every one of `bypass`/`unlock`/`repair`/`write`/`resume` (`requireSafeSession`), so no adjustment to this exception's matching grammar could fix that, and the diagnostic MUST NOT fabricate, guess, or truncate a placeholder session id to force a command to fit — that would target the wrong state, which is worse than printing nothing. In this specific case, and only this case, the diagnostic message contract (above) is replaced by this one instead: **the message MUST state plainly that no session id could be resolved, MUST instruct the operator to end the current session and start a new one (the host mints a fresh, valid `session_id` for the new session, which is unaffected by this one's resolution failure), and MUST still state that `pwd` (the Inspection Bash Exception, which needs no session identity at all) remains usable in the interim.** This is a concrete, testable diagnostic, not "the operator figures it out": AC0 asserts the exact three elements above appear, and asserts no `--session`-bearing command is ever printed in this branch.
- AC0 and AC9 (§4) MUST include a subprocess test proving, **for every degradation case where a safe session id is resolvable** (§1.3's no-safe-session-id branch is a separate, mutually exclusive case with its own three-element diagnostic contract, not a recovery-command-executable case at all — the two are never asserted together for the same fixture), that the recovery command remains executable, and that a bare `pwd` is never denied on a fresh session (0–2 tool calls), **enforced mechanically by the Inspection Bash Exception above — not by an unenforced aspiration** — `pwd`'s guarantee is unconditional and does not depend on session-id resolution at all, unlike the five `handoff.mjs` subcommands. Every other rule in this spec that can restrict mutating tools (Hard-Degraded Mode, the incomplete-scan lower-bound restriction, the depth-only-fallback restriction) restricts "mutating tools other than the Recovery Exception and the Inspection Bash Exception," so bare `pwd` and the recovery CLI are structurally exempt from every one of them, not just the ones caused by a false/unproven signal. Once Phase 1's real occupancy telemetry exists and a session's baseline text genuinely measures above `HARD_PCT` before any tool calls (AC2's overlay/host-token cases), every *other* mutating tool is correctly denied — that is the gate working as intended — but bare `pwd` specifically remains allowed by the Inspection Bash Exception even then, because it is inert with respect to context consumption regardless of band.

## 2. Normative Architecture & Signal Derivation

Do not enable §2 enforcement, and do not treat AC1–AC9 as satisfied, until a real host implementation of these fields exists and has been verified end-to-end against this adapter (§2.7's deployment-order rule). Beyond that gate, §2.3's crash-atomic commit protocol is itself a draft sketch with named open cut-points (see its own note) requiring a dedicated crash-consistency design and property/crash-injection-testing pass before Phase 1 can be implemented, not just before it can be enabled — treat §2 as the target architecture and problem statement, not a build-ready spec. The Phase 0 hotfix (§1.2) is the change that ships to fix the reported outage; this section remains the target design for exact occupancy tracking once host support lands and its commit protocol is hardened. The Recovery Exception and the Inspection Bash Exception (§1.3) apply here without exception, including to every Hard-Degraded trigger defined below — this is the guarantee that holds regardless of how §2.3's open cut-points are eventually resolved.

### 2.1. Active Context Epoch & Host-Authenticated Compaction Provenance
Transcripts record session history cumulatively. The **active context epoch** is defined as the slice of transcript from the most recent valid host-authenticated compaction boundary to the current end of the transcript.

1. **Session Identity & Path Hardening:**
   - `input.session_id` MUST match `/^[A-Za-z0-9._-]{1,128}$/`. Any other value → Hard-Degraded Mode.
   - All state paths under `.adlc/state/` are constructed only from this validated id (never from raw path fragments).
2. **Host-Authenticated Compaction Provenance (MAC-bound, non-tool-writable):**
   Compaction boundaries are authenticated via an adapter-owned out-of-band host event channel that tools cannot forge:
   - **Key lifecycle (process-per-hook safe):** On **every** PreToolUse / session-init envelope, the host delivers the same session-ephemeral HMAC key `K_host` (and `ledger_expected` boolean) through the privileged host IPC / native subprocess pipe. Adapters MAY hold `K_host` only in process memory for the duration of that invocation; they MUST NOT write it under the workspace, `.adlc/`, or any tool-reachable path. Concurrent PreToolUse processes each receive `K_host` independently from the host — there is no shared key file.
   - Host event log and ledger live under host-owned state: `$ADLC_HOST_STATE_DIR/host-events-${session_id}.jsonl` and `$ADLC_HOST_STATE_DIR/ledger-${session_id}.json` (mode `0600`), where `ADLC_HOST_STATE_DIR` comes only from the host envelope and MUST be outside the workspace. Adapters open events `O_RDONLY` with §2.2 symlink/descriptor authentication. The host process is the only writer of the events file.
   - Host events are a versioned discriminated union, append-only in `$ADLC_HOST_STATE_DIR/host-events-${session_id}.jsonl` (one event per line). Every event carries `{ v: 1, type, session_id, seq, timestamp_ms, ...typeFields, mac }` where `seq` is a host-monotonic per-session counter and
     `mac = HMAC-SHA256(K_host, canonicalJson({ v, type, session_id, seq, timestamp_ms, ...typeFields }))`
     (domain-separated by `type`; unknown `type` is retained for seq accounting only).
   - **Event application vs certificate lookup (distinct):**
     - *Application:* only events with `seq == host_event_seq_hw + 1, host_event_seq_hw + 2, …` contiguous from the ledger watermark are applied once; gaps → Hard-Degraded Mode; already-applied `seq <= host_event_seq_hw` are **not** re-applied and are **not** treated as replays.
     - *Lookup:* a previously applied `compact_boundary` event remains a valid certificate for authenticating the persistent transcript boundary on every later evaluation (match by offset/hash/identity), without requiring a fresh seq.
     - A *true* replay attack is a newly appended log line that reuses a prior `seq` or breaks contiguity → Hard-Degraded Mode.
   - **`type: "compact_boundary"` fields:** `{ transcript_dev, transcript_ino, byte_offset, boundary_line_sha256, pre_boundary_size }`.
     **Offset/hash semantics (normative):** `byte_offset` is the zero-based absolute file offset of the **first byte of the boundary record's JSON text** (the byte of `{` or the first content byte of that line). `exactBoundaryLineBytes` is the exact on-disk bytes of that record **including** its terminating `0x0A` LF if present in the file; if the file uses CRLF, the CRLF pair (`0x0D0A`) is included and hosts MUST normalize only via emitting LF-only transcripts going forward (CRLF transcripts are accepted if both sides hash the same raw bytes). `pre_boundary_size === byte_offset` (bytes strictly before the boundary line). Active-epoch content begins at `epochStartOffset = byte_offset` (boundary line included in the new epoch). `boundary_line_sha256 = SHA-256(exactBoundaryLineBytes)`.
   - **`type: "transcript_rotate"` fields:** `{ old_dev, old_ino, old_size_highwater, old_prefix_sha256, new_dev, new_ino, new_initial_size, new_prefix_sha256 }`.
   - **`type: "tool_lifecycle"` fields:** `{ handle, signature, phase }` where `phase ∈ {"flushed","completed","cancelled","failed"}` and `handle`/`signature` match ledger pending identity.
     **Lifecycle lattice (sticky):** legal merges use rank `completed < flushed = cancelled = failed` for removal purposes — once `flushed|cancelled|failed` is applied for a handle, later `completed` events cannot downgrade it. Persist `pendingList[i].terminal_phase` (or equivalent in `seenHandles`) so terminal evidence is sticky across evaluations. Duplicate identical terminal phases are no-ops; contradictory terminals for the same handle (`flushed` vs `cancelled`) → Hard-Degraded Mode.
   - A transcript record is accepted as a compaction boundary ONLY when:
     a) `(record.type === 'system' || record.role === 'system')` AND `record.session_id === input.session_id`;
     b) `(record.subtype === 'compact_boundary' || record.event === 'compaction' || record.is_compacted === true || record.phase === 'compact')`;
     c) `typeof record.summary === 'string' && record.summary.length > 0`; AND
     d) There exists a `compact_boundary` host event whose `session_id`, `transcript_dev`, `transcript_ino`, and `byte_offset` match the current transcript identity and boundary offset, whose `boundary_line_sha256` equals `sha256(exactBoundaryLineBytes)`, whose `mac` verifies under `K_host`, whose `seq` has been successfully applied (or is being applied in this transaction), and whose `timestamp_ms` is within ±5s of the boundary record's host timestamp when present.
   - Missing `K_host`, MAC verification failure, or event-file authentication failure → Hard-Degraded Mode (never silently treat as “no compaction”).
   - **Unregistered Compaction Boundary Handling:** Any well-formed record in the transcript carrying compaction-like keys that lacks a MAC-verified host event is strictly treated as ordinary dialogue/payload text; the scanner does NOT reset the epoch on it and continues scanning backwards toward authentic boundaries or start of file.
   - **Malformed Record Handling:** Structurally invalid JSON lines or unrecoverable UTF-8 encoding errors strictly trigger **Hard-Degraded Mode** (`observed.depth = NaN, observed.pct = NaN`).
3. **Epoch Isolation & Summary Accounting:**
   When scanning backwards from the end of the file, the active epoch begins at the first compaction boundary satisfying host-authenticated provenance.
   - The compaction boundary record itself is included in the chronological projection as the first record of the new epoch. Its exact projection is:
     - Claude Code / Codex (both): append `[system] ${normalizedContent(record.summary)}` and **do not** also project `message.content` / `text` / `content` from that same boundary record (summary is the sole payload for the boundary line).
   - The active epoch identity key is computed as:
     $$\text{epochKey} = `${stat.dev}_${stat.ino}_${compactionByteOffset}_${sha256(compactionLine)}`$$
   - If no compaction record exists, $\text{epochKey} = `${stat.dev}_${stat.ino}_0_root`$.
4. **Cross-Evaluation Transcript Monotonicity (bounded chunk-chain commitment):**
   Transcripts are authenticated as an append-only chain of fixed-size chunks (`CHUNK = 1 MiB`) with an explicit partial tail:
   - Ledger `transcript_hw` stores `{ transcript_dev, transcript_ino, size_highwater, full_chunk_count, last_full_chain_sha256, partial_len, partial_chain_sha256, active_epoch_chunk_hashes: hex[] }` inside the whole-ledger MAC (§2.3).
   - Full chunks: `chain_i = sha256(bytes[i*CHUNK, (i+1)*CHUNK) || chain_{i-1})` with `chain_{-1} = 32 zero bytes`. After `full_chunk_count` complete chunks, a partial tail of `partial_len ∈ [0, CHUNK)` has `partial_chain_sha256 = sha256(bytes[full_chunk_count*CHUNK, size_highwater) || last_full_chain_sha256)` (if `partial_len=0`, `partial_chain_sha256 = last_full_chain_sha256`).
   - **Growth algorithm:** If `stat.size > size_highwater` and the prior tip was partial:
     1. Reread bytes `[chunkStart, size_highwater)` and verify they hash with `last_full_chain_sha256` to the **stored** `partial_chain_sha256`. Mismatch → Hard-Degraded Mode (mutation of previously committed partial bytes).
     2. Only then reread `[chunkStart, stat.size)` (or stream the new suffix after the verified prefix) and recompute the extended partial/full chain.
     3. When the partial reaches `CHUNK`, seal it as a full chunk (`full_chunk_count++`, update `last_full_chain_sha256`) and continue.
     Never treat a mid-chunk suffix as an independent chain node.
   - **Active-epoch integrity:** After determining `epochStartOffset` (0 or compaction byte offset), verify **every** chunk overlapping `[epochStartOffset, size1)` against `active_epoch_chunk_hashes`. Each entry is `{ chunk_index, byte_start, byte_length, sha256 }` where `chunk_index = floor(byte_start / CHUNK)`, `byte_start = max(epochStartOffset, chunk_index*CHUNK)`, `byte_length` covers through `min(size1, (chunk_index+1)*CHUNK) - byte_start`, and `sha256 = SHA-256(exact bytes[byte_start, byte_start+byte_length))` (**raw chunk slice**, not chained). On epoch advance, rebuild the array from scratch for the new `[epochStartOffset, size)`. On growth within an epoch, re-verify unchanged entries byte-identically before extending/replacing the tip entry. Same-size mutation anywhere in the active epoch is detected. Chunks strictly before `epochStartOffset` are not re-verified each eval; hosts that rewrite pre-epoch history MUST emit `transcript_rotate`.
   - Transcript bytes SHOULD be host-owned (host-passed `transcript_fd` or path under a host-controlled non-workspace directory). If the transcript path is workspace-tool-writable, active-epoch chunk verification is mandatory and insufficient tip-only checks are non-conformant.
   - **Shrink:** `stat.size < size_highwater` → Hard-Degraded Mode.
   - **`transcript_rotate` state machine:** Apply only a newly contiguous MAC-verified `transcript_rotate` event where:
     - `old_dev/old_ino/old_size_highwater` match ledger `transcript_hw`, and `old_prefix_sha256` equals the ledger tip commitment (`partial_chain_sha256` if `partial_len>0` else `last_full_chain_sha256`);
     - opened descriptor matches `new_dev/new_ino`;
     - `sha256(bytes[0, new_initial_size))` (streaming) **equals** `new_prefix_sha256` (constant-time compare) **before** any state rebuild;
     Then: (1) reset `transcript_hw` from the verified new prefix (chunk-chain built over `[0, new_initial_size)`); (2) keep `pendingList`/`seenHandles`/`invocationSeq`; (3) set `epochKey` to the new root or authenticated boundary on the new file; (4) rebase in-flight pendings as on compaction. Failure of any check → Hard-Degraded Mode. Identity change without this event → Hard-Degraded Mode.
   - **Post-scan path check:** Immediately before durable ledger commit, `postLstat = lstat(transcript_path)`. If `postLstat.dev/ino` differ from the opened descriptor's `stat`, do not commit; if a matching unused `transcript_rotate` event exists, retry once under that event; else Hard-Degraded Mode.
   - Lock-held work is covered by the four independent per-phase budgets defined in §2.2.3 (`MAX_SCAN_WALL_MS` + `MAX_TOKENIZE_WALL_MS` + `MAX_RECONCILE_WALL_MS` + `MAX_PERSIST_WALL_MS`), not by a single shared timer — see `MAX_LOCK_HELD_WALL_MS` in §2.2.1.

### 2.2. Lossless Binary Reverse-Chunk Framing & Lock-Protected Scan Linearization
To ensure atomic, race-free, and lossless reading from live append-only JSONL files without symlink spoofing, replacement races, or stale scan windows:

1. **Unified Lock-Protected Transaction Protocol:**
   Every `PreToolUse` evaluation executes as a single serialized transaction protected by an exclusive cross-process lock:
   - **Lock location (non-tool-writable):** Prefer a host-passed lock descriptor in the privileged envelope (`input.host_lock_fd`). If absent, open `flock` on `$ADLC_HOST_STATE_DIR/ledger-${session_id}.lock` where `ADLC_HOST_STATE_DIR` is supplied only by the host envelope and MUST resolve outside the workspace (and outside any path tools may `unlink`/`rename`). Opening a lock under `.adlc/` or the workspace is a spec violation → Hard-Degraded Mode.
   - **Primitive:** POSIX platforms use `flock(LOCK_EX | LOCK_NB)` on the host-owned descriptor. On platforms without flock, use exclusive `O_CREAT|O_EXCL` lockfile create in `ADLC_HOST_STATE_DIR` containing `{ pid, starttime_boot_ns, lease_expires_ms }`.
   - **Crash release:** flock locks are released automatically when the owning process dies (descriptor close). **Prefer flock;** lockfile fallback is allowed only when flock is unavailable:
     1. `lstat` the lock path; open existing lock with `O_RDONLY|O_NOFOLLOW` and verify `fstat` matches `lstat` ino/dev.
     2. Read `{ pid, starttime_boot_ns, lease_expires_ms, ino }`. Reclaim is permitted only if pid is dead **and** lease expired **and** recorded `ino` equals the inspected inode.
     3. Atomic takeover: `linkat`/`renameat` a newly `O_CREAT|O_EXCL`-created candidate lock onto the path **only if** a compared `rename`/`replace` API binds to the inspected inode (e.g. Linux `renameat2` with `RENAME_EXCHANGE` against a directory entry verified by ino, or delete via `unlinkat` on an fd opened with `O_PATH` to that ino where available). If the platform cannot bind reclaim to the inspected inode, the adapter MUST refuse lockfile fallback and Hard-Degrade instead of racing.
     4. Two waiters racing a true stale lock: exactly one reclaim succeeds; the loser restarts from step 1.
   - Supported max concurrent PreToolUse waiters per session: `MAX_PARALLEL_TOOLS = 8`. `MAX_LOCK_HELD_WALL_MS = MAX_SCAN_WALL_MS + MAX_TOKENIZE_WALL_MS + MAX_RECONCILE_WALL_MS + MAX_PERSIST_WALL_MS` (= 900ms by default, §2.2.3). Acquire with timeout `LOCK_WAIT_MS = MAX_PARALLEL_TOOLS * MAX_LOCK_HELD_WALL_MS + 500` (= 7700ms), so a full queue of conforming evaluations each consuming their whole lock-held budget cannot itself cause a later waiter to time out and Hard-Degrade. Fail-closed on timeout.
   - Transaction boundary spans: Lock Acquisition → Descriptor Verification → Bound Scan Snapshot → Bounded Backward Streaming Scan → High-Water Mark Reconciliation → Exact Depth & Token Evaluation → Durable Atomic Ledger Save → Lock Release.
2. **Pre-Open Symlink Rejection & Descriptor Authentication:**
   - Execute `lstat = fs.lstatSync(transcript_path)`.
   - If `lstat.isSymbolicLink() === true`, IMMEDIATELY REJECT and enter Hard-Degraded Mode.
   - Open descriptor using `fd = fs.openSync(transcript_path, fs.constants.O_RDONLY | (fs.constants.O_NOFOLLOW || 0))`.
   - Authenticate `stat = fs.fstatSync(fd)`:
     - `stat.isFile()` MUST be true (reject sockets, FIFOs, device nodes).
     - `stat.dev === lstat.dev && stat.ino === lstat.ino` MUST be true.
     - `stat.uid === process.getuid()` MUST be true (owner-matching enforcement; skip only when `process.getuid` is undefined, and then require Hard-Degraded unless `ADLC_ALLOW_FOREIGN_UID=1` is set by the host envelope — never by tools).
   - If path or descriptor authentication fails, enter Hard-Degraded Mode.
3. **Bounded Streaming Backward Seek (No Token-Based Early Termination):**
   - Read size `size1 = stat.size`. If `size1 === 0`, return active epoch with `diskDepth = 0`, `activeContextText = ""`.
   - Stream backwards in 512 KiB binary `Buffer` chunks.
   - Find newline bytes (`0x0A`) directly in binary buffers; join chunk fragments at raw byte level before UTF-8 decoding.
   - **Resource budgets (normative):**
     - `MAX_ACTIVE_CONTEXT_BYTES = 8 MiB` of reassembled active-epoch payload (excluding bytes before the accepted compaction boundary).
     - **Per-phase wall-clock budgets, not one shared deadline.** A single 200ms budget covering descriptor checks, hashing, scanning up to 8 MiB, exact tokenization, reconciliation, and a durable fsync-ing ledger write has no realistic cold-cache/throttled-I/O margin, and treating any overrun as proof of hard pressure converts ordinary slow hardware into a blanket denial unrelated to context usage. Budgets are tracked independently:
       - `MAX_SCAN_WALL_MS = 200`: descriptor checks + binary backward scan + chain-hash verification only.
       - `MAX_TOKENIZE_WALL_MS = 300`: pinned-tokenizer `countTokens` over the assembled `activeContextText` + baseline + pending text.
       - `MAX_RECONCILE_WALL_MS = 100`: high-water reconciliation and band evaluation (no I/O).
       - `MAX_PERSIST_WALL_MS = 300`: ledger temp write, commit-journal write, renames, and directory fsync (§2.3's crash-atomic commit).
       Each budget is independently overridable via `ADLC_CONTEXT_{SCAN,TOKENIZE,RECONCILE,PERSIST}_WALL_MS` (integer ms, host/operator-set only) for slower or constrained environments. `LOCK_WAIT_MS` (§2.2.1) is derived from `MAX_LOCK_HELD_WALL_MS`, the sum of all four (900ms by default) — there is no other combined-timer definition anywhere in this spec; any earlier wording implying a single shared `MAX_SCAN_WALL_MS` covers all lock-held work is superseded by this paragraph.
     - **Timeout consequence is scoped to what timed out, not blanket Hard-Degraded Mode:**
       - Exceeding `MAX_SCAN_WALL_MS` or `MAX_TOKENIZE_WALL_MS` before independently proving `HARD_DEPTH` (§4 AC1's depth-count termination, §2.2.3(c)) falls back to depth-only evaluation using whatever tool-call count was accumulated before the deadline (same lower-bound rule as the Phase 0 hotfix, §1.2.2: a lower bound is only safe to act on once it reaches `HANDOFF_DEPTH` — a `WARN`-range or lower lower-bound restricts mutations to the Recovery Exception and the Inspection Bash Exception until a complete scan succeeds, rather than claiming a full allow) — `observed.pct` is omitted, `observed.depth` is the accumulated lower-bound count. This is not a truncated `exactPct`; it is an honest statement that the percentage couldn't be computed in time, which is a narrower claim than "the session is unrecoverable."
       - **Correction to an earlier draft of this paragraph:** reconciliation (§2.3.3 steps a–g: matching pending entries against `diskOccurrences`) runs *before* exact depth/token evaluation (§2.3.3 step h), not after — so "the already-computed `observed` values" do not yet exist when `MAX_RECONCILE_WALL_MS` can be exceeded, and an earlier claim that they do was wrong and contradicted §2.6's classification. Exceeding `MAX_RECONCILE_WALL_MS` is therefore governed by the same rule as a scan/tokenize timeout (§1.2.2's lower-bound principle): whatever partial reconciliation was completed yields a lower-bound depth, evaluated the same way (only trusted as-is once it reaches `HANDOFF_DEPTH`; otherwise restricted to the Recovery Exception + Inspection Bash Exception) — never a full, unproven allow, and never treated as though a hard percentage that was never actually computed is "retained." §2.6's exclusion list already classifies `MAX_RECONCILE_WALL_MS` this way; this paragraph now agrees with it. Exceeding `MAX_PERSIST_WALL_MS` before the ledger rename starts, or after the journal rename completes, is a separate, later step (persistence, after depth/pct genuinely have been computed) and does not discard that already-computed decision — only durable persistence is degraded (a warning, per §2.3's resolved commit rule) when the decision was `deny` or touched no new pending state; an `allow` decision instead requires the durable watermark advance before it can be returned (§2.3). Exceeding `MAX_PERSIST_WALL_MS` **between the two renames** is a torn-commit state and enters Hard-Degraded Mode for that evaluation per §2.3.
       - Full Hard-Degraded Mode (`observed.depth = NaN`) remains reserved for cases where depth itself cannot be established at all (malformed transcript, symlink/descriptor authentication failure, etc. — §2.6's fail-closed list), consistent with §2.4.2c.
     - `MAX_SINGLE_RECORD_BYTES = 2 MiB`. A single newline-delimited record exceeding this → Hard-Degraded Mode (depth cannot be established for that record; this is a malformed-input case, not a budget case).
   - Backward streaming terminates when the first of the following holds:
     a) A host-authenticated compaction boundary is found;
     b) Start of file ($0\text{ bytes}$) is reached;
     c) Accumulated tool call count strictly reaches `HARD_DEPTH (40)`: depth-hard is proven. Continue scanning **only as far as needed** to locate an authenticated compaction boundary or start-of-file for `epochKey` correctness (still subject to byte/time budgets). Set `observed.pct = undefined` (omit pct) when the full active-epoch projection was not assembled; consumers MUST treat depth-hard alone as denying mutations. Do **not** emit a partial exactPct; OR
     d) `MAX_ACTIVE_CONTEXT_BYTES` or `MAX_SCAN_WALL_MS` is exceeded → depth-only fallback per the scoped-timeout rule above (do not silently truncate occupancy; do **not** guess a token percentage; do **not** treat the timeout itself as proof of hard pressure).
   - **Exact tokenization rule:** Tokenize only the fully assembled chronological `activeContextText` (plus baseline and pending texts) after the scan completes and records are reversed. Do **not** early-exit on partial newest-to-oldest token estimates — BPE merges are not additive across prepended older text, so partial scans cannot prove hard-band occupancy.
4. **Bound Scan Snapshot & Post-Scan Authentication:**
   - Before scanning, record `size1`, extend the chunk chain for growth per §2.1.4, and verify all active-epoch chunk hashes overlapping the prospective scan range. The scan MUST read only through `[0, size1)` via the already-open `fd` using positional reads — never re-resolve the path mid-scan.
   - After scanning, re-verify those same active-epoch chunk hashes. Mismatch → in-place mutation race → Hard-Degraded Mode.
   - Check `size2 = fs.fstatSync(fd).size`. If `size2 !== size1`, transcript grew concurrently **after** the snapshot. Do **not** incorporate the new suffix; optionally retry (up to 2) with a fresh snapshot. Never mix bytes from two snapshots.
   - Path identity changes follow `transcript_rotate` rules; otherwise Hard-Degraded Mode.
   - Commit updated `transcript_hw` (including `active_epoch_chunk_hashes`) for `size1`.

### 2.3. Per-Adapter Projection Grammar, Signatures & Lifecycle-Bound Ledger
1. **Normative Context Projection Grammar (exact serialization):**
   - Scan collects raw newline-delimited records from newest to oldest until a stop condition; then **reverse** them into chronological order (oldest → newest) before projection.
   - Projected records are concatenated with a single `\n` (U+000A) separator between records. **Normative:** no trailing `\n` after the final record (final byte is never LF unless the final record's payload itself ends with LF). Empty component sets contribute nothing (no blank leading/trailing separators). No other separators are inserted.
   - Structured content normalization before string projection:
     - If `content` / `text` / `message.content` is a string, use it as-is.
     - If it is an array of blocks, join block text fields with `\n` after projecting each block; unknown block shapes → `canonicalJson(block)`.
     - If it is a non-null object, use `canonicalJson(value)`.
     - If it is `null` or `undefined`, use the empty string.
   - **Claude Code Projection:**
     - Compaction boundary records (already authenticated per §2.1): append only `[system] ${normalizedContent(record.summary)}` (see §2.1.3); skip other fields on that record.
     - `record.type === 'system'` (non-boundary): append `[system] ${normalizedContent(record.message?.content ?? record.text)}`; if the record additionally carries a non-empty `record.summary` (e.g. a compaction-shaped record that failed boundary authentication per §2.1's "Unregistered Compaction Boundary Handling" — treated as ordinary payload, not skipped), also append `[system_summary] ${normalizedContent(record.summary)}` on its own line. A record whose only non-empty field is `summary` MUST NOT project as empty text: unregistered ≠ unweighed.
     - `record.type === 'user'`: append `[user] ${normalizedContent(record.message?.content ?? record.text)}`.
     - `record.type === 'assistant'`: iterate `record.message?.content` blocks in array order. For `'tool_use'`, append `[tool_use:${block.id || ''}:${block.name}] ${canonicalJson(block.input || {})}`, record occurrence in `diskOccurrences`, and increment `diskDepth`. For `'text'`, append `[assistant] ${block.text || ''}`. Other block types: append `[assistant_block:${block.type || 'unknown'}] ${canonicalJson(block)}`.
     - `record.type === 'tool_result'`: append `[tool_result:${record.tool_use_id || ''}] ${normalizedContent(record.content)}`.
     - Unrecognized non-empty record types under `claude-code/context-v1`: **Hard-Degraded Mode** (do not project). New shapes require `claude-code/context-v2`.
   - **Codex Projection:**
     - Compaction boundary records (already authenticated per §2.1): append only `[system] ${normalizedContent(record.summary)}` (see §2.1.3); skip other fields on that record.
     - `record.role === 'developer' || record.role === 'system'` (non-boundary): append `[system] ${normalizedContent(record.content)}`; if the record additionally carries a non-empty `record.summary` (compaction-shaped but unauthenticated, per §2.1), also append `[system_summary] ${normalizedContent(record.summary)}` on its own line, for the same reason as the Claude Code rule above — an unregistered summary is still real payload text and must be weighed.
     - `record.role === 'user'`: append `[user] ${normalizedContent(record.content)}`.
     - `record.role === 'assistant'`: iterate `record.tool_calls` in array order. For each function call, parse arguments as JSON (failing closed if unparseable), append `[tool_use:${call.id || ''}:${call.function.name}] ${canonicalJson(parsedArgs)}`, record occurrence in `diskOccurrences`, and increment `diskDepth`. Then, if `record.content` is present, append `[assistant] ${normalizedContent(record.content)}`.
     - `record.role === 'tool'`: append `[tool_result:${record.tool_call_id || record.call_id || ''}] ${normalizedContent(record.content)}`.
     - Unrecognized non-empty record roles under `codex/context-v1`: **Hard-Degraded Mode** (do not project). New shapes require `codex/context-v2`.
2. **Deterministic Canonical JSON Helper:**
   ```js
   function canonicalJson(val) {
     if (val === null || typeof val !== 'object') return JSON.stringify(val);
     if (Array.isArray(val)) return `[${val.map(canonicalJson).join(',')}]`;
     const keys = Object.keys(val).sort();
     return `{${keys.map(k => `${JSON.stringify(k)}:${canonicalJson(val[k])}`).join(',')}}`;
   }
   ```
   - Reject `undefined`, `bigint`, functions, symbols, and cyclic structures by entering Hard-Degraded Mode when encountered inside tool inputs subject to `canonicalJson`.
3. **Lifecycle-Bound Pending Ledger State Machine:**
   - Ledger entries are NEVER deleted by arbitrary TTL or timers. Entries are removed strictly upon:
     a) Disk reconciliation when their target occurrence count appears on disk; OR
     b) Authoritative host `tool_lifecycle` of `flushed`, `cancelled`, or `failed`; OR
     c) Immediate cleanup when a gate evaluation returns `deny`.
     Note: `completed` without `flushed` does **not** remove an entry.
   - Ledger schema (normative JSON object). The ledger resides only under `$ADLC_HOST_STATE_DIR` (non-workspace, host-owned). Tools MUST NOT be able to create/replace/unlink it. Integrity still uses `ledger_mac` as defense-in-depth:
     ```json
     {
       "v": 1,
       "session_id": "string",
       "ledger_generation": 0,
       "epochKey": "string",
       "invocationSeq": 0,
       "host_event_seq_hw": 0,
       "baseline_id": "string",
       "baseline_sha256": "hex",
       "transcript_hw": {
         "transcript_dev": 0,
         "transcript_ino": 0,
         "size_highwater": 0,
         "full_chunk_count": 0,
         "last_full_chain_sha256": "hex",
         "partial_len": 0,
         "partial_chain_sha256": "hex",
         "active_epoch_chunk_hashes": [ { "chunk_index": 0, "byte_start": 0, "byte_length": 0, "sha256": "hex" } ]
       },
       "pendingList": [
         {
           "handle": "string",
           "invocation_ordinal": 0,
           "tool_name": "string",
           "canonical_input": "string",
           "canonical_pending_text": "string",
           "signature": "string",
           "targetDiskCount": 0,
           "timestamp": 0,
           "decision": "allow|deny|null",
           "terminal_phase": "null|completed|flushed|cancelled|failed"
         }
       ],
       "seenHandles": { "handle": { "decision": "allow|deny", "signature": "string", "completed": true, "terminal_phase": "null|completed|flushed|cancelled|failed" } },
       "epochFlushCounts": { "signature": 0 },
       "ledger_mac": "hex"
     }
     ```
     `seenHandles` are durable tombstones for sealed host identities. Hosts MUST mint globally unique handles per session (no reuse). If `seenHandles` would exceed `MAX_SEEN_HANDLES = 65536`, enter Hard-Degraded Mode rather than silently evicting (eviction would re-admit delayed retries as new work). `epochFlushCounts` counts flushed occurrences of each signature **within the current `epochKey` only**; on epoch advance it is reset to `{}` after migration.
     `ledger_mac = HMAC-SHA256(K_host, canonicalJson({ v, session_id, ledger_generation, epochKey, invocationSeq, host_event_seq_hw, baseline_id, baseline_sha256, transcript_hw, pendingList, seenHandles, epochFlushCounts }))`.
     `ledger_generation` initializes at 1 on first create and increments by 1 on every successful commit.
     **Crash-atomic commit with independent watermark:** Directory `fsync` of `$ADLC_HOST_STATE_DIR` after renames is attempted on every commit and its outcome is always distinguished from the two renames that precede it: a failed directory fsync MUST NOT be conflated with a failed rename. Every `PreToolUse` evaluation is its own process (§2.1.2's "process-per-hook safe"), so there is no in-memory ledger state to carry into a later evaluation — what the *next* process sees is whatever is durably on disk; an **ordinary next process start** (no crash, both renames complete, dir-fsync succeeded or is still pending but the directory entry is intact) opens the same files the current process just wrote via a fresh read and sees the correct, just-committed state directly.
     - `commit_mac = HMAC-SHA256(K_host, canonicalJson({ v: 1, type: "commit_journal", session_id, ledger_generation, ledger_sha256 }))` — this is the one and only formula; the `type` field is part of the signed/verified object itself (serialized in the journal alongside `commit_mac`, not injected only during verification), using the same session-scoped `K_host` as every other MAC in this document. Verification recomputes this over the read journal bytes (including its own `type` field) and compares constant-time; a mismatch is treated identically to a missing/absent journal (unpaired, torn state).
     - **An `allow` decision for a mutating tool is not returned to the caller until the full commit — both renames *and* the durable watermark advance — has succeeded.** This is the rule that closes the gap in every partial-persistence case below: a `deny` decision is always safe to return immediately regardless of persistence outcome (denying is the fail-safe direction — if it isn't durably recorded, a retry simply re-evaluates and denies again, no protection is lost), but an unrecorded `allow` is exactly the kind of accounting/anti-replay loss the ledger exists to prevent, so it is never handed out ahead of its own durability. Concretely: if the full commit sequence below has not completed, an otherwise-`allow` decision is converted to Hard-Degraded Mode for that one invocation instead (protected, as always, by the unconditional Recovery Exception). Non-mutating decisions (inspection tools, the Recovery Exception itself) never touch `pendingList` and are unaffected by any of this.
     - **A failed directory fsync alone, with both renames and the watermark advance already durable and verified intact on the next read, MUST NOT put the session into Hard-Degraded Mode** (this is the single normative rule — the "mandatory" and "best-effort" language in earlier drafts of this section contradicted each other and both must be read as superseded by this paragraph): it is logged as a durability warning and the read proceeds normally.
     - **Any other torn/mismatched/stale/incomplete commit state — detected via the journal↔ledger MAC pair, the `ledger_generation >= envelope.min_ledger_generation` check, or simply not having reached the durable watermark advance yet — enters Hard-Degraded Mode for that evaluation, not depth-only fallback.** This covers: failure/timeout before the ledger rename starts; a crash/timeout between renaming the ledger and renaming the commit journal (mismatched pair); a crash/timeout after the journal rename but before the watermark advance is durable (the "safe zone" only truly begins once the watermark is written, not merely once both renames are done); and a crash in the post-watermark/pre-fsync window that rolls the directory back to a stale pair (caught by the generation check). The reason this differs from every other depth-only-fallback case in this spec is that the ledger is not merely an occupancy cache — its `pendingList`/`seenHandles`/`host_event_seq_hw` are the anti-replay and deny-tombstone state (§2.3.3's "first decision wins" invariant). Silently reconstructing depth from the disk-scanned transcript alone would discard that state and could re-admit an already-denied handle or undercount an unflushed in-flight call — a correctness/security regression, not just an unproven percentage. The Recovery Exception (§1.3) is unconditional precisely so that this case never lets a Hard-Degraded response strand an operator: `bypass`/`unlock`/`repair`/`write`/`resume` and all inspection tools remain reachable, and `repair`/`write` are exactly the operator-driven tools that re-establish a clean ledger.
     - `min_ledger_generation` in the host's durable, authenticated envelope advances only after both renames succeed (not gated on the directory-fsync outcome, since renames — not the directory fsync — are the file-content commit signal); this is what makes the generation check above able to detect a rollback, and it is the specific step whose durability gates whether an `allow` decision may be returned (above).
     - Commit order: (1) write+fsync ledger temp; (2) write+fsync `ledger-${session_id}.commit.json` temp `{ v: 1, type: "commit_journal", session_id, ledger_generation, ledger_sha256, commit_mac }`; (3) rename ledger; (4) rename commit journal; (5) advance envelope `min_ledger_generation` to the committed generation and durably persist that advance (host-durable — this is the step that closes the "safe zone," not step 4 alone); (6) attempt dir fsync (best-effort by the rule above; its failure is logged as a durability warning, not gated on). Renaming the ledger before the journal (reversed from earlier drafts — any other paragraph in this document that still says "rename journal, then rename ledger" is stale and superseded by this one) means a crash between steps 3 and 4 leaves the *new* ledger paired with the *old* journal — a mismatch the MAC-pair check already detects — rather than a new journal referencing a ledger temp path that may not exist; either ordering is detectably torn, this ordering makes the torn state's cause unambiguous for an operator reading the diagnostic.
     - **§2.3's commit protocol is a draft sketch, not an implementation-ready state machine — say so plainly rather than let "tracked" imply "resolved."** This two-phase commit's exact behavior at every possible crash instant — e.g. whether `ledger_generation >= min_ledger_generation` needs strict equality instead of `>=` to catch a watermark-not-yet-advanced window; whether a directory-fsync failure needs to gate returning a mutating `allow` (not just be logged) to be crash-durable against power loss, not just process crash; how a `deny`-path failure between the two renames avoids landing in the same torn state as an `allow`-path failure; **whether a `MAX_RECONCILE_WALL_MS` timeout's partial result is actually a safe lower bound (partial reconciliation can leave already-disk-flushed pending entries un-removed, double-counting them into an inflated total — an *upper*-bound risk this document's "trust it once it crosses `HANDOFF_DEPTH`" rule does not currently distinguish from the *lower*-bound risk a partial scan/tokenize has) and whether a `MAX_TOKENIZE_WALL_MS` timeout should instead trust an already-exact, fully-reconciled depth normally rather than treating it as unproven; whether this gate's replay/first-decision-wins guarantee (§2.3.3) needs to extend to execution-level idempotency of the underlying mutating tool call itself (a duplicated PreToolUse envelope replaying a sealed `allow` decision prevents duplicate *ledger accounting* but does not, by itself, prevent the host from executing the tool a second time — that is arguably a host/tool-runtime responsibility this adapter-only gate cannot itself enforce, but the boundary needs to be stated explicitly, not left implicit); and **§2.5/AC7's Codex Mutating/Inspection Sets, which still name a single literal `execute_command` identity and assume one fixed `tool_input` shape — §1.3 corrected this for Phase 0's Recovery/Inspection Exceptions with its own narrow, purpose-built exact allowlist (deliberately not `isShellToolName`, for the safety-direction reason given there), grounded in the real, already-shipped `toolNameOf`/command-text-collector from `plugins/adlc-codex/hooks/adlc-handoff-gate.mjs` for field-reading only; §2.5's Phase 1 table still needs its own correction before Phase 1 implementation — likely `isShellToolName` IS the right predicate there, since §2.5 governs the denial/classification side, not an unconditional-allow exception, but that judgment call belongs to Phase 1's own implementation work, not this hotfix** — all of the above are real gaps, and this revision does not claim to have closed all of them. They are deliberately not chased indefinitely in this document for two reasons: (1) Phase 1 cannot be enabled at all until real host support for `K_host`/lock/ledger capabilities lands (§1.1, §2's banner) — no implementation exists yet for these cut-points to be wrong *in*; and (2) the governing invariant that actually matters for safety is already unambiguous and does not depend on resolving them: **any detected or suspected torn/uncertain commit state enters Hard-Degraded Mode, never a silently-returned unrecorded `allow`, and the Recovery Exception plus the Inspection Bash Exception (§1.3) are unconditional and do not depend on the ledger/lock/persistence machinery at all** — so getting a specific cut-point's classification wrong during Phase 1's eventual implementation degrades to "an operator has to run `repair`," never to "the session is stranded." Before Phase 1 enforcement is enabled, its implementation MUST close every cut-point above with crash-injection tests (kill at each numbered step, kill mid-syscall where the platform allows it) — this is implementation-phase property/crash-injection testing work, not further specification prose.
     Missing key, MAC mismatch, or deletion of the ledger when host envelope `ledger_expected=true` (durable host session flag, re-supplied on every invocation and persisted by the host outside tool reach) → Hard-Degraded Mode. Host restart MUST preserve `ledger_expected` for the live session id or terminate the session.
   - Within the locked critical section:
     a) Load `$ADLC_HOST_STATE_DIR/ledger-${session_id}.json` (fail-closed if corrupt). Verify `ledger_mac` over the entire body. Enforce §2.1.4 prefix monotonicity before continuing. Apply any new host events with `seq > host_event_seq_hw` in order; update `host_event_seq_hw`.
     b) **Baseline binding:** If ledger has no baseline yet, set `baseline_id` / `baseline_sha256` from the host envelope. If the envelope's `baseline_id` or `sha256(baseline_context_text)` differs from the ledger → Hard-Degraded Mode (no silent baseline swap mid-session). Host must issue a new session to change baseline.
     c) **Pre-migration reconciliation on compaction (phase-specific):** When `currentEpochKey !== ledgerState.epochKey` (whether the authenticating `compact_boundary` certificate was applied in this transaction or looked up from a previously applied event):
        1. Do **not** rescan historical prefixes and do **not** use cross-epoch flush totals.
        2. For each pending entry, classify by its sticky `terminal_phase` (lattice above):
           - `cancelled` or `failed` → remove (no disk occurrence required).
           - `flushed` → remove (flush is authenticated; count toward epoch flush accounting before reset).
           - `completed` only (no flushed/cancelled/failed) → **retain as in-flight** (completion ≠ transcript flush).
           - no lifecycle event → **retain as in-flight** (still running across compaction; this is the AC1 compaction-during-in-flight case).
        3. Set `ledgerState.epochKey = currentEpochKey`; set `epochFlushCounts = {}`.
        4. Rebase retained in-flight pendings: `entry.targetDiskCount = (diskOccurrences.get(entry.signature) || 0) + indexAmongSameSignatureInPending + 1` using post-boundary `diskOccurrences` only.
     d) **Ordinary High-Water Reconciliation (same epoch):** Prefer **handle-keyed** reconciliation. Build `diskHandles` from projected tool_use ids present in the active epoch. Filter `pendingList`:
        - Remove if `entry.handle` is non-synthetic and `diskHandles.has(entry.handle)` (exact tool-call identity matched on disk), OR
        - Remove if sticky `terminal_phase` is `cancelled`/`failed`, OR
        - Remove if sticky `terminal_phase` is `flushed` (host flush attestation is authoritative even if bytes not yet scanned), OR
        - **Retain** if `terminal_phase` is `completed` only, or absent.
        - **Missing-ID / synthetic handles** (`*_seqN`): do **not** consume another pending's credit via aggregate signature counts. Instead maintain per-signature FIFO of synthetic pending handles; each newly observed unmatched disk occurrence of that signature retires exactly the head of that FIFO (one credit → one handle). Never apply a disk occurrence to a non-head entry.
        When removing a reconciled entry, write/update `seenHandles[handle] = { decision: prior, signature, completed: true, terminal_phase }`.
     e) Compute invocation parameters:
        - `canonicalInput = canonicalJson(input.tool_input || {})`
        - `signature = `${input.tool_name}_${sha256(canonicalInput)}``
        - Always: `ledgerState.invocationSeq += 1`; `invocation_ordinal = ledgerState.invocationSeq` (every invocation, including host-identified ones).
        - Prefer sealed host identity: `handle = input.tool_use_id || input.id` when present and non-empty.
        - Otherwise: `handle = `${signature}_seq${invocation_ordinal}``. Never use `pendingList.length`, `Date.now()`, or `Math.random()` as identity.
        - Persist `invocation_ordinal` on the pending entry.
        - `canonicalPendingText = `[tool_use:${handle}:${input.tool_name}] ${canonicalInput}``
     f) **Handle Deduplication & Replay (first decision wins):**
        - If `seenHandles[handle]` exists: if signature mismatch → Hard-Degraded Mode. Else return the recorded `decision` without mutating depth/pending (including completed and denied tombstones).
        - If `handle` is already in `ledgerState.pendingList`: if signature mismatch → Hard-Degraded Mode. Else if `entry.decision` is non-null, return that decision **without** re-evaluating bands and **without** removing the pending entry (an earlier allow may still be executing). Else update `timestamp` only.
        - Otherwise continue to append.
     g) Otherwise, compute `targetDiskCount = (diskOccurrences.get(signature) || 0) + pendingCountForSig + 1`, and append `{ handle, tool_name: input.tool_name, canonical_input: canonicalInput, canonical_pending_text: canonicalPendingText, signature, targetDiskCount, timestamp: Date.now() }`.
     h) Evaluate Normative Depth and Exact Pinned Tokenizer Occupancy.
     i) Persist `entry.decision` to the pending record before returning. If decision is `deny`, remove `handle` from `pendingList` and set `seenHandles[handle] = { decision: "deny", signature, completed: true, terminal_phase: entry.terminal_phase }`. On `allow`, keep the pending entry (with `decision: "allow"`) and set `seenHandles[handle] = { decision: "allow", signature, completed: false, terminal_phase: entry.terminal_phase }` until flush/cancel/fail/disk reconciliation marks `completed: true`. Never reverse an existing non-null `entry.decision` on replay.
     j) Update `transcript_hw` per §2.1.4, recompute `ledger_mac`, and **Durable Atomic Ledger Save** under `$ADLC_HOST_STATE_DIR` only:
        - Create a randomized temp name `ledger-${session_id}.${randomHex}.tmp`.
        - `open(tmp, O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW, 0600)` — never follow symlinks; never reuse a predictable `.tmp` path; if `EEXIST`, retry with a new random name.
        - Authenticate the temp fd via `fstat` (regular file, owner match, nlink==1).
        - Write ledger bytes including monotonic `ledger_generation`, `fsync` fd.
        - Write the commit journal, then rename the **ledger** temp into place, then rename the **journal** temp into place, then durably advance the envelope watermark (see crash-atomic protocol above for why this order and what each intermediate state means).
        - **If the invocation's computed decision is `allow` for a mutating tool, that decision is not returned until the watermark advance in step (5) above is durable.** Any failure/timeout anywhere before that point (before the ledger rename starts, between the two renames, or after the journal rename but before the watermark write) converts the response to **Hard-Degraded Mode for this invocation** — never a silently-returned, unrecorded `allow` — detected via the journal↔ledger MAC pair, the generation-watermark check, or simply the watermark step not having completed. The Recovery Exception (§1.3) remains available throughout.
        - **If the invocation's computed decision is `deny` (or the invocation touches no pending-mutation state — e.g. a `WARN`-only allow that added no new pending entry beyond what disk reconciliation already accounts for), the same persistence failures are safe to treat as depth-only fallback per §2.4.2c** rather than Hard-Degraded Mode: a `deny` costs nothing to re-derive on retry, and temps are unlinked, previous ledger+journal remain in place as a valid, paired, non-stale generation.
        - Directory `fsync`, per the resolved rule above: attempted always, after the watermark advance; a failure here alone, with both renames and the watermark already durable and verified intact on the next read, records a durability warning and proceeds — it does not deny mutations.

### 2.4. Semantic Date & Sentinel Validation, Normative Depth & Pinned Tokenizers
1. **Normative Depth Formula:**
   $$\text{observed.depth} = \text{diskDepth} + \text{ledgerState.pendingList.length}$$
   - Evaluated against: `WARN_DEPTH = 20`, `HANDOFF_DEPTH = 30`, `HARD_DEPTH = 40`.
2. **Semantic Calendar Date & Sentinel Validation:**
   Define `isValidCalendarDate(yearStr, monthStr, dayStr)`:
   - Parse integers $Y, M, D$. Validate $1 \le M \le 12$.
   - Leap year: $\text{isLeap} = (Y \pmod 4 === 0 \land Y \pmod{100} \ne 0) \lor (Y \pmod{400} === 0)$.
   - Days in month: $[31, \text{isLeap} ? 29 : 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31][M - 1]$. Assert $1 \le D \le \text{daysInMonth}$.
   - **Model Families & Pinned Tokenizers:**
     Normative regexes are JavaScript `RegExp` source strings (alternation is a real `|`, never a literal pipe). Evaluate rows top-to-bottom; first full-match wins. After a family match, if a date suffix capture is present it MUST pass `isValidCalendarDate`; `latest` / `preview` sentinels are allowed only where listed.

   - **Capacity + encoding resolution (no silent 8k masquerade):**
     - Known model from `MODEL_FAMILY_TABLE`: `{ encoding, capacityTokens } = table row`.
     - Host envelope MAY supply a privileged versioned registry overlay `host_model_registry` mapping additional ids/aliases → `{ encoding, capacityTokens }`; overlays are MAC-bound in the envelope and take precedence for exact id match.
     - `ADLC_CONTEXT_WINDOW_TOKENS`, if set, parses strictly as integer ∈ [8,000, 2,000,000] and caps `capacityTokens = min(detectedOrOverlayCapacity, override)` for known/overlay models.
     - Unknown model paths (exactly one must hold):
       a) Overlay entry supplies both `encoding` and `capacityTokens` (override may still cap capacity downward); OR
       b) Host-token occupancy path is active (`host_live_tokens*` + `host_capacity_tokens` present) — client tokenizer init is waived; capacity denominator follows the host-capacity rule below; OR
       c) Else → **depth-only fallback, not Hard-Degraded Mode.** An unrecognized model id with no overlay and no host-token path means only the *exact-occupancy percentage* is unavailable — it does not mean the session's actual tool-call depth is unknown. The adapter omits `observed.pct` (leave it `undefined`, not `NaN`) and evaluates solely on `observed.depth` (§2.4.1's `WARN_DEPTH`/`HANDOFF_DEPTH`/`HARD_DEPTH`, computed the same way regardless of tokenizer availability). A fresh session with an unrecognized model id and 0–2 tool calls therefore stays in the `allow` band — it is not sent to Hard-Degraded Mode merely for lacking a capacity/encoding mapping. Reserve full Hard-Degraded Mode (`observed.depth = NaN`) for cases where depth itself cannot be computed (malformed transcript, unreadable file, etc. — §2.6's actual fail-closed list), not for a missing tokenizer mapping.
     - A bare `ADLC_CONTEXT_WINDOW_TOKENS` without encoding (overlay or table) and without the host-token path does not by itself unlock a percentage; the session runs under the depth-only fallback above until a valid encoding/capacity pairing exists.
3. **Exact Pinned Tokenizer Occupancy Evaluation:**
   - If using the registered serialization path (client-side `countTokens`), initialize the pinned tokenizer for the resolved encoding. If tokenizer is unavailable or fails to initialize, enter Hard-Degraded Mode. If using the host-token path exclusively, client tokenizer initialization is waived.
   - **Baseline lifecycle (single contract):** At session initialization the host envelope MUST supply `{ baseline_id, baseline_context_text }` — the exact host-assembled system prompt + tool-schema text the model will see, not reconstructed from the transcript. Adapters persist `baseline_id` and `baseline_sha256 = sha256(baseline_context_text)` in the ledger (§2.3). `baselineTokens = countTokens(baseline_context_text)`.
     - **No-duplication contract (host-exclusion only):** The host MUST NOT also append `baseline_context_text` into the transcript epoch body. Adapters therefore count baseline **only** via `baselineTokens` and count transcript projections **only** via `activeContextText` — they MUST NOT subtract or pattern-match baseline text out of projections.
     - If a projected epoch somehow begins with a `[system] ` record whose payload equals `baseline_context_text` exactly, treat that as host-contract violation → Hard-Degraded Mode (detectable double-count risk), rather than attempting subtraction.
   - **Mandatory exact-occupancy paths for target adapters (non-optional):**
     **Selected production paths:** Claude Code uses `claude-code/context-v1` (companion checked into this repo). Codex uses `codex/context-v1` (companion checked into this repo). Both MAY additionally accept the host-token path when the host advertises `occupancy_bind_mac` support (negotiated via envelope field `occupancy_protocol: "host-tokens-v1"|"serialization-v1"`; default `serialization-v1`). An adapter is non-conformant if it implements neither path:
     1. **Host-token path (preferred):** After lock acquisition and snapshot binding, the host envelope (or a host RPC invoked under the lock) supplies authenticated integers `host_live_tokens` / `host_live_tokens_with_pending` and `host_capacity_tokens`, plus `serialization_id`, together with `occupancy_bind_mac = HMAC-SHA256(K_host, canonicalJson({ session_id, size1, tip: partial_len>0?partial_chain_sha256:last_full_chain_sha256, epochKey, pending_digest, host_live_tokens, host_live_tokens_with_pending, host_capacity_tokens, serialization_id }))` where
        `pending_digest = SHA-256(UTF8(canonicalJson(pendingBindArray)))` and `pendingBindArray` is the array of `{ invocation_ordinal, handle, signature, tool_name, canonical_input }` for all pending entries **including** the current invocation, ordered by ascending `invocation_ordinal` (unique per session). Stale counts that do not MAC-bind to the locked snapshot → Hard-Degraded Mode. Domain validation (fail-closed): every host count MUST satisfy `Number.isSafeInteger(n) && n >= 0`; `host_capacity_tokens` MUST satisfy `Number.isSafeInteger(n) && n >= 8000 && n <= 2000000`; when pending is non-empty, `host_live_tokens_with_pending >= host_live_tokens`. Adapters set `liveTokens = host_live_tokens_with_pending` (or `host_live_tokens` when `pendingList` is empty). **No client-side addition of separately tokenized pending segments.** After computing `exactPct`, require `Number.isFinite(exactPct) && exactPct >= 0`; else Hard-Degraded Mode.
        **Denominator rule:** `capacityTokens = host_capacity_tokens`, then apply the downward operator cap if `ADLC_CONTEXT_WINDOW_TOKENS` is set (`min`). If a table/overlay capacity is also known and `host_capacity_tokens` differs from that resolved capacity by more than 0, enter Hard-Degraded Mode (disagreement). If only the host-token path supplies capacity (unknown model case b), `host_capacity_tokens` is authoritative subject to the downward cap.
     2. **Registered serialization path:** `serialization_id` is one of the normative ids below, and the adapter builds `canonicalLiveContextText` byte-identical to that contract, then calls `countTokens` **once** on the full string (baseline + active epoch + pending), never component-wise.
        - `claude-code/context-v1`: exact byte framing published in `packages/context-handoff/serialization/claude-code-context-v1.md` (normative companion in `packages/context-handoff/serialization/`). Covers system/user/assistant/tool_result/tool_use framing as emitted to the Claude Code model API for that host version.
        - `codex/context-v1`: exact byte framing published in `packages/context-handoff/serialization/codex-context-v1.md` (normative companion in `packages/context-handoff/serialization/`).
        - **General rule (not limited to the summary case below — this is the load-bearing sentence):** the v1 companions are immutable and, being hand-authored documents, are not guaranteed to enumerate byte framing for every record/block shape §2.3's depth-accounting projection grammar can ever produce (its own catch-all rules — `[system_summary]`, and Claude's `[assistant_block:${type}] ${canonicalJson(block)}` for any non-`text`/non-`tool_use` block type — exist precisely because §2.3 must remain total over whatever the host emits, while a byte-exact companion can only enumerate what its authors anticipated). **Whenever the active epoch contains anything §2.3 projects that the negotiated v1 companion has no defined byte sequence for — an unregistered/unauthenticated `.summary` field (§2.1's "Unregistered Compaction Boundary Handling"), an `assistant_block` of a type the companion doesn't frame, or any future such gap — the registered-serialization occupancy path (this option) MUST NOT be used for that evaluation.** Computing `exactPct` from v1 framing in that case would silently undercount, since v1 has no byte sequence for that content. Fail over to the host-token path (option 1) if available; if neither path can produce a trustworthy `exactPct`, omit `observed.pct` and fall back to depth-only evaluation (§2.4.2c) — which is already correct, because §2.3's projection grammar (unlike v1's serialization contract) is total and so `observed.depth`/injection-resistance are unaffected by any v1 framing gap. This rule is what makes v1's genuine immutability ("framing changes require a new serialization_id") safe rather than silently lossy: v1 never needs to grow a new frame to stay correct, because anything it can't frame simply routes around it rather than being dropped. A future `claude-code/context-v2` / `codex/context-v2` companion covering every §2.3 shape would let the exact-occupancy path stop deferring in these cases, but is not required to ship the Phase 0 hotfix or to close the depth-accounting/injection-resistance gap this revision fixes.
     Acceptance fixtures for AC2/AC3 MUST include at least one non-degraded capture per adapter proving path (1) or (2) on a fresh session, including the compatibility tuple (serialization_id, host_protocol_version∈[1,1], tokenizer package version, tokenizer asset hash) and independent host-produced differential token captures covering: baseline-only; each projected record class (system/user/assistant/tool_use/tool_result); multi-block and multi-call ordering; pending calls; compaction summaries; empty fields; and values immediately below and at WARN/HANDOFF/HARD thresholds — for every supported encoding including `gemini-sp`.
   - §2.3 projection grammar remains required for **depth** accounting and injection resistance. It is not an occupancy oracle except insofar as a registered `serialization_id` document explicitly maps projection records to host bytes.
   - $$\text{exactPct} = \frac{\text{liveTokens}}{\text{capacityTokens}} \times 100$$
   - `exactPct` is an unrounded IEEE-754 float and **MAY exceed 100**. It is never clamped for band evaluation.
   - **Unrounded Exact Threshold Evaluation:**
     - `isWarn = exactPct >= WARN_PCT (50.0)`
     - `isHandoff = exactPct >= HANDOFF_PCT (60.0)`
     - `isHard = exactPct >= HARD_PCT (80.0)`
   - **Emitted Signal:** `observed.pct = exactPct` (unrounded floating-point number passed to `evaluateBands`; rounded to 1 decimal place only for human-readable logs).
   - `observed.bytes`: Retired (left `undefined`).
   - **Golden oracles:** Implementations MUST ship host-capture fixtures under `packages/context-handoff/test/fixtures/calibration/` keyed by `serialization_id`, with committed host-visible token-input blobs (or recorded `host_live_tokens`) and `*.expected.json` `{ encoding, tokenCount, serialization_id }`. AC percentages are derived only from those host-bound oracles, never from byte-length heuristics or unlabeled synthetic projections.

### 2.6. Fail-Closed Error Contract with Positive-Registry Read-Only Recovery
To prevent silent fail-open while preserving read-only diagnostic and recovery capabilities:
- **This is the authoritative list — §2.4.2, §2.2.3, and §2.3 govern the cases explicitly excluded below, and take precedence over any older/duplicate wording elsewhere in this document.** If `input.transcript_path` is absent, empty, non-string, unreadable, is a symlink, fails descriptor authentication, fails `postLstat` linearization, fails `fstatSync` / `fs.readSync`, contains unrecoverable decoding errors, malformed newline-terminated JSON, tokenizer initialization failure, lock timeout (`LOCK_WAIT_MS`), missing/`K_host` MAC failure, host-event descriptor failure, whole-ledger MAC failure, transcript prefix mismatch/shrink/in-scan mutation/unauthenticated identity transition, host-event seq gap/replay, missing serialization_id/host token fields, `MAX_SINGLE_RECORD_BYTES` exceeded, or unhandled schema drift within the active epoch:
  - The adapter returns `observed.depth = Number.NaN` and `observed.pct = Number.NaN`.
  - `classifyBandSignal(NaN)` classifies the signal as invalid/hard-degraded.
  - **Explicitly NOT in this list (depth-only fallback per §2.4.2c / §2.2.3's scoped-timeout rule instead of Hard-Degraded Mode):** an unknown model with no overlay/override/host-token path; `MAX_ACTIVE_CONTEXT_BYTES` or a phase wall-clock budget (`MAX_SCAN_WALL_MS`/`MAX_TOKENIZE_WALL_MS`/`MAX_RECONCILE_WALL_MS`) exceeded before `HARD_DEPTH` is independently proven; and `MAX_PERSIST_WALL_MS` expiring, or a ledger durable-save failure, **when the invocation's computed decision was `deny` (or touches no new pending-mutation state)** — regardless of which persistence step it occurred at (§2.3's resolved commit rule).
  - **Explicitly back IN this list (Hard-Degraded Mode, not depth-only — §2.3):** any persistence failure or `MAX_PERSIST_WALL_MS` expiry occurring **before the full commit (both renames plus the durable watermark advance) completes, when the invocation's computed decision was `allow` for a mutating tool** — this is true whether the failure lands before the ledger rename, between the two renames, or after the journal rename but before the watermark write; an unrecorded `allow` risks the same anti-replay/deny-tombstone loss as a torn commit, so it is never returned early. Also included: any detected torn/mismatched/stale commit state regardless of decision (journal↔ledger MAC mismatch, or a stale generation via the watermark check). The Recovery Exception (§1.3) applies here as everywhere else in this list.
  - In Hard-Degraded Mode:
    - **Positively Authenticated Inspection Tools** matching the host's positive registry:
      - **Claude Code:** Positively authenticated `View`, `GlobTool`, `GrepTool`, `LS`
      - **Codex:** Positively authenticated `read_file`, `grep_search`, `list_dir`, `view_image`
      are **ALLOWED** (`permissionDecision: "allow"`), enabling agents to inspect files and execute handoff recovery workflows.
    - **The Recovery Exception and the Inspection Bash Exception (§1.3) are evaluated before this rule**, not as members of the positive-registry set above: a `Bash`/`execute_command` invocation matching the allowlisted `handoff.mjs bypass|unlock|repair|write|resume` pattern, or the exact literal `pwd`, is **ALLOWED** even though `Bash`/`execute_command` are themselves in the Mutating Set — unconditionally, including in Hard-Degraded Mode and including once Phase 1 telemetry correctly hard-degrades a genuinely over-capacity session (§1.3's last bullet). Without this, "execute handoff recovery workflows" in the line above is aspirational text with no enforcement path, since the CLI in bullet's own claim requires a mutating shell tool the very next bullet denies.
    - **All Other Tools** (mutating built-ins, unclassified tools, extensible/MCP tools, spoofed names) are **DENIED** (`permissionDecision: "deny"`) with a clear diagnostic denial message explaining telemetry degradation and, per §1.3, including the literal recovery command **when a safe session id is resolvable, or the no-safe-session-id branch's three-element diagnostic (no other recovery command) when it is not** — the two are mutually exclusive, never both, and never neither.

### 2.7. Rollout, Negotiation & Session Migration
- Envelope MUST include `occupancy_protocol` (`serialization-v1` | `host-tokens-v1`) and `host_protocol_version`.
- Existing sessions that began before this gate version: host MUST either (a) drain/end the session and start a new one under the new protocol, or (b) supply a one-shot `session_migrate_v1` host event that installs a fresh MAC-valid ledger at `ledger_generation=1` with `min_ledger_generation=1`, resetting `transcript_hw`/`epochKey` (tied to the old pre-MAC scheme) but **carrying `seenHandles` forward unmodified** rather than clearing it — sealed terminal tombstones are exactly what stop a delayed retry from being re-admitted as new work (§2.3.3), and migration is not a legitimate reason to lose that protection; `MAX_SEEN_HANDLES` already bounds its size. `pendingList` resets to empty only because it is REQUIRED to already be empty by the quiescence check below — it is never migration's job to discard a non-empty one. Silent dual-read of pre-MAC ledgers is forbidden. **The adapter MUST NOT trust a bare host claim of quiescence for `pendingList` — it already has the authoritative local answer.** Before applying a `session_migrate_v1` event, the adapter checks its own current, locally-verified ledger state: if `pendingList.length > 0` (an in-flight, not-yet-flushed mutating call), the migration event is rejected (Hard-Degraded Mode for that evaluation, not silently applied) rather than discarding live in-flight state. Migration proceeds only when the adapter's own pre-migration read shows an empty `pendingList` — the same self-verification the transcript-rotate and compaction paths already require elsewhere in this section, applied here instead of trusting the event alone.
- Deployment order: host support for envelope fields + `$ADLC_HOST_STATE_DIR` **before** enabling adapter enforcement. If the adapter sees an older host lacking required fields → Hard-Degraded Mode with a diagnostic naming the missing capability (not a false exactPct).
- Downgrade/rollback of host below `host_protocol_min` mid-session → Hard-Degraded Mode; operators must drain sessions before rolling back hosts.

## 4. Acceptance Criteria & Test Verification Suite

### AC0 Criteria: Immediate Hotfix & Recovery Exception (Phase 0 — ships independently, blocks nothing on host support)

This is the minimum bar for closing this ticket. AC1–AC9 govern the Phase 1 host-protocol design and remain gated on real host support per §2's banner; AC0 does not depend on any of it.

- **Fresh-session regression (the exact outage case):** a brand-new session, 0–2 prior tool calls, on Claude Code or Codex, under Phase 0 as currently deployed — no real occupancy telemetry, so `observed.pct` is never populated — on any model (including an unrecognized model id with no overlay and no host-token path) → `pwd` (or the equivalent minimal Bash/`execute_command` invocation) is ALLOWED. This is the primary regression test and MUST run against the real `handoff-gate.mjs` / `adlc-handoff-gate.mjs` hook entry points end-to-end (not just `bands.mjs`/`thresholds.mjs` unit-level math), because the production incident was a hook-payload-to-decision integration failure, not a pure threshold-math failure. Once Phase 1 wires up real occupancy telemetry, a fresh session whose baseline text genuinely measures above `HARD_PCT` (AC2's overlay/host-token cases) legitimately denies every *other* mutating tool — that is correct protective behavior, not this regression — but exact-literal `pwd` specifically remains allowed even then, structurally, by the Inspection Bash Exception (§1.3), which is unconditional across every band in both phases. Verify: the fresh-session fixture in `handoff-deny.test.mjs` asserts `permissionDecision === 'allow'` for both hosts.
- **Large-baseline fresh-session regression (the specific mechanism, not just its symptom):** the same fresh-session case above, but with a baseline system-prompt/MCP-schema/rules blob deliberately sized between 256 KiB and 8 MiB (i.e., large enough to have tripped the old, now-retired `MAX_SCAN_BYTES` ceiling, but well within `MAX_ACTIVE_CONTEXT_BYTES`) → the scan completes within `MAX_SCAN_WALL_MS`, establishes exact depth 0–2, and **ordinary mutators — `Edit`, `Write`, and a normal (non-`pwd`) `Bash` invocation — are ALLOWED, not merely `pwd`**. Testing only bare `pwd` here would let a regression survive where `MAX_SCAN_BYTES` (or an equivalent low ceiling) is still silently present and the scan never completes, in which case only the Inspection Bash Exception would be masking a still-broken hotfix underneath it. This fixture MUST use a >256 KiB baseline specifically — a small-transcript fixture cannot detect this regression at all.
- **Compaction-boundary decoy (proves the boundary policy in §1.2.2, not just the scan budget):** a transcript containing a well-formed, structurally plausible compaction-boundary-shaped record (`subtype: "compact_boundary"` or equivalent) partway through, with 0–2 real tool calls after it and substantially more before it — under Phase 0 (no `K_host`, nothing can authenticate this marker) the scan MUST NOT stop at it and MUST NOT report the low post-boundary count as the session's depth; it continues scanning through to start-of-file (or the resource budgets) and reports the true cumulative count.
